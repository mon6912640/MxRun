# MxRun 命令模型设计（草案）

> 起草：2026-09-13
> 目的：**不照抄 AltRun 的数据模型**。先用现代眼光把真实数据分类分析清楚，再定 MxRun 自己的命令模型。
> 样本：AltRun 真实数据 `Bin\ShortCutList.txt`（本机路径见 `local/机器环境.md`）—— 76 行 = **72 条真实命令 + 4 条空行（分隔线）**
> 与其它文档的关系：`AltRun交互规格.md` 仍是**交互**权威（按键、流程、时序）；本文只管**数据模型与执行语义**。冲突时：按键/流程看规格，模型看本文。
> **落地状态**：§4 的模型已在 **P0-1 落地**（`src/store.rs`），含旧库迁移与触发词加权搜索，实测通过（见 `开发进度.md` §2.6）。执行器是 P0-2，尚未实现。

## 1. 样本的原始结构

```
F权重 | 编码列| 关键字 | 名称      | 命令行
F116  |       | Computer | 我的电脑  | ::{20D04FE0-3AEA-1069-A2D8-08002B30309D}
F6    |No_Encoding| cmd  | Dos窗口   | cmd /k %p
F12   |URL_Query| b      | 百度搜索引擎| http://www.baidu.com/s?wd=
```

- `F<n>` = 累计执行次数。**注意：这些值大多不是用户的使用记录，而是作者模板里的预置权重**（查证见 §6.1.1）。
- **编码列统计：60 条空、`No_Encoding` 4 条、`URL_Query` 4 条、`UTF8_Query` 4 条**——这 12 条的用法有问题，见 §3.1。
- 空行 = 分隔线（`scBlank`），列表里的分组用，共 4 条（外加文件末尾的换行）。

## 2. 按"这东西本质上是什么"分类（72 条全覆盖）

## 3. 从数据里挖出的四条设计证据

### 3.1 `param_type` 一个枚举干了四件事（最大的历史包袱）

源码 `Unit/untShortCutMan.pas:737-793` 里，`ParamType` 同时决定：

1. **要不要做变量替换**——`ptNone` 直接跳过整个分支，`{%c}`/`{%wd}` 会被**原样**传给程序
2. **输入从哪来**——`{%c}`→剪贴板、`{%wd}`→前台窗口句柄、`{%wt}`→窗口标题、`{%wc}`→窗口类名；而且是 if/else-if 链，**只认第一个命中的**
3. **怎么编码**——原样 / URL 编码 / UTF-8 编码（对拿到的字符串统一施加，不管它来自用户输入还是剪贴板）
4. **要不要弹参数框**——四个变量都没有，才弹

**数据上的铁证**：

| 命令 | 编码列 | 真实意图 | 说明什么 |
|---|---|---|---|
| `@.\WinCtl.exe ShowOnly {%wd}` | `No_Encoding` | **根本不需要用户输入** | 必须设成非 `ptNone`，否则 `{%wd}` 不被替换 → 这个配置纯粹是"打开替换开关" |
| `@.\WinCtl.exe Hide {%wd}` | `No_Encoding` | 同上 | 同上 |
| `http://www.baidu.com/s?wd={%c}` | `URL_Query` | 剪贴板内容要 URL 编码 | 编码器作用在**剪贴板**上，跟"参数"无关 |
| `http://www.google.com/search?q={%c}` | `UTF8_Query` | 剪贴板内容要 UTF-8 编码 | 同上 |

也就是说这 4 条配置**不是"参数类型"，是被缺陷逼出来的开关**。一个字段兼职四职，是后面所有功能都难加的根因。

### 3.2 执行修饰是字符串前缀，而且判定顺序敏感

`@.\WinCtl.exe MinAll`（显示桌面）——`@+` / `@-` / `@` 写在命令行**开头**表示最大化 / 最小化 / 隐藏启动，判定还必须先 `@+`/`@-` 再 `@`。这是把"启动方式"塞进字符串的典型做法：既和命令本身冲突（命令真要以 `@` 开头就完了），又得靠顺序约定救。

### 3.3 两个外部依赖搬不过来

- **`WinCtl.exe`**（E 类 6 条里的 4 条）：作者随 ALTRun 一起分发的小工具，MxRun 没有它 → 照搬这几条 = 死条目
- **`.\ALTRun.ini`**（C 类 1 条）：指向 AltRun 自己的配置文件，对 MxRun 无意义

好消息：这几件事 Win32 API 直接就能做（`MinimizeAll`、`ShowWindow`、前台窗口句柄/标题/类名本来就是现成可取的），所以**内建实现**比搬运更省事。

### 3.4 数据里有失效项，而原版不做健康检查

`Upgrade`（sohu 博客链接，权重 F15 说明当年真的常用）、`IE浏览器`（已退役）、`VeryCD`、`搜狗MP3`——这四条现在是否还有效我无法从本地判断，但**原版的"校验"只检查命令行语法，不检查可用性**。现代启动器应当有健康标记（未知 / 可用 / 失效）。

## 4. MxRun 命令模型（草案）

### 4.1 设计原则

1. **分类沿两条正交的轴**，不按"这东西叫什么名字"分：
   - **轴一：动作效果**（封闭集合）——程序实际能"做出"的结果就那么几种
   - **轴二：来源 Provider**（开放轴）——导入器、开始菜单、`@` 文件搜索都挂这里
2. **参数是动作的属性**，不是一种类型；"输入从哪来 / 怎么编码 / 怎么插进去"是三件独立的事
3. **一个条目可以有多个动作**（回车 = 默认动作，其余挂修饰键）——文件搜索结果需要"打开 / 打开所在目录 / 复制路径"
4. 每个字段都要能回答："导入那 72 条时它装什么？`@` 搜文件时它装什么？"
5. **核心枚举保持封闭且极小**：加新能力优先加"动词"，而不是加"类型"

### 4.2 结构

```rust
/// 一个能被选中并激活的结果。静态条目落库，动态条目（如 Everything 结果）只活在本次查询。
Item {
    id: String,                  // 稳定 id —— frecency 按它存，**迁移时绝不能变**
    title: String,               // 主显示
    subtitle: String,            // 次显示（可空）
    keywords: Vec<String>,       // 触发词，第 1 个为主（原版只支持 1 个）
    actions: Vec<Action>,        // 至少 1 个，第 1 个是默认动作
    arg: ArgSpec,                // 参数规格（"要不要输入"是属性，不是类型）
    launch: LaunchMode,          // 替代 @+ / @- / @ 前缀
    source: Source,              // 出处：provider + external_id
    health: Health,              // Unknown / Ok / Broken
}

/// 动作：一个条目可以挂多个
Action {
    label: String,               // 菜单上的名字（"打开" / "打开所在目录" / "复制路径"）
    effect: Effect,
}

/// 轴一：动作效果（封闭集合，加能力就加动词）
enum Effect {
    Open   { target: String },   // 交给系统打开：程序/文件/目录/网址/协议/CLSID/shell:
    Run    { line: String },     // 起进程跑一句命令行（可带参数、工作目录）
    Builtin{ verb: BuiltinVerb },// 程序内自己做：窗口控制、电源、"把输入当命令跑"
    Copy   { text: String },     // 放进剪贴板
    Reveal { path: String },     // 在资源管理器里定位
    // 预留缝：Custom { provider: String, payload: String }  —— 插件/脚本自定义，现在不实现
}

enum BuiltinVerb {
    MinimizeAll, ShowDesktop,                 // 显示桌面 / 最小化全部
    HideForegroundWindow, ShowForegroundWindow,// 隐藏 / 恢复前台窗口
    Shutdown, Reboot,
    RunInput,                                 // 原版的「运行」：把输入当命令执行（也用于将来的兜底）
}

/// 参数规格：三件事拆开
ArgSpec {
    source: ArgSource,   // None | Prompt | Clipboard | ForegroundId | ForegroundTitle | ForegroundClass
    encode: Encoder,     // Raw | UrlQuery | Utf8Percent
    insert: InsertMode,  // None（不用参数）| Replace（替换命令里的 {p}）| Append（追加到末尾，搜索引擎用）
}

enum LaunchMode { Normal, Maximized, Minimized, Hidden }
enum Health     { Unknown, Ok, Broken }

/// 轴二：出处 —— 导入幂等、识别"源里已删除"、互不干扰都靠它
Source {
    provider: String,     // "seed" | "manual" | "shortcutlist" | "startmenu" | "everything" | ...
    external_id: String,  // 源内的唯一标识：行号、快捷方式路径、文件完整路径……
}
```

### 4.3 Provider：轴二怎么扩展（导入解析挂这里）

```rust
enum ProviderKind {
    Index,   // 启动时建好索引、内存打分（瞬时）——手工条目、导入条目、开始菜单、UWP
    Query,   // 输入时才跑：**异步 + 可取消 + 有超时**——`@` → es.exe、将来的脚本/插件
}

trait Provider {
    fn id(&self) -> &str;                       // "startmenu" / "everything" / ...
    fn kind(&self) -> ProviderKind;
    fn query(&self, input: &str, cancel: &CancelToken) -> Vec<Item>;  // Query 型实现它
}
```

**前缀注册表**（`@` 是模式切换，不是关键字）：

```
前缀 "@"  → provider "everything"      （只在输入**开头**生效；出现在中间当普通字符）
前缀 ">"  → provider "run"（将来）
```

存在配置里（`cfg:` 表），可改、可关。

**导入幂等的四条规则**（靠 `Source` 实现）：

1. 同一 `(provider, external_id)` 重复导入 → **覆盖更新**，不产生重复
2. 源里已消失 → 标记失效，不静默留、也不静默删
3. 重新导入**不碰**手工条目的触发词/动作（provider 不同就是不同条目）
4. 加新导入器 = 新 provider + 一个"外部记录 → Item"映射函数，**核心枚举不动**

### 4.4 与原版的关键对照

| AltRun | MxRun | 为什么 |
|---|---|---|
| `param_type` 4 值枚举 | `ArgSpec { source, encode, insert }` 拆开 | 一个枚举干四件事 → 拆成三件独立的事；`{%wd}` 不再需要"假装有参数" |
| 只有一个"命令行"字段 | `actions: Vec<Action>` + 封闭的效果集合 | 一个条目可以有多个动作（打开/定位/复制路径）；执行方式不再靠字符串前缀表达 |
| `@+` `@-` `@` 前缀 | `LaunchMode` 字段 | 前缀会与命令冲突、靠顺序约定 |
| 单个关键字 | `keywords: Vec<String>` | 一条命令可记多个习惯（`b`/`bd`/`baidu`），主关键字排第一 |
| `%p` 与 `{%p}` 双语法 | 只保留 `{p}` | 双语法是历史遗留 |
| 占位符只替换第一个 | 全部替换 | 原版缺陷 |
| 空关键字/命令行 → 静默变空行 | 拒绝 + 提示 | 原版坑 |
| 依赖 `WinCtl.exe` | `Effect::Builtin` 内建 | 去外部依赖 |
| 关键字按正则匹配（`*`→`.*`） | nucleo 模糊匹配 + 触发词加权 | MxRun 已有更好的 |
| 无来源概念，全靠文件行位置 | `Source { provider, external_id }` | 导入要幂等、要能识别"源里删了"、要能多来源共存 |
| 无 | `health` 字段 | 样本里确实有失效项 |
| 分隔线（`scBlank`）是一种类型 | **不是条目**，导入时跳过 | 原版自己都不显示它（见 §6.6） |

## 5. 明确不照搬（模型层面，补充规格的"②故意不照搬"）

- 4 值 `param_type` 枚举，以及它兼职的四件事
- `@` 系列字符串前缀
- 单关键字 + 关键字正则匹配
- 只替换第一个占位符
- `ptNone` 就不替换变量
- 空值静默降级成空行
- 对 `WinCtl.exe` 之类外部小工具的依赖
- **"分隔线"作为一种类型**（原版自己都不在结果列表显示，见 §6.6）
- **"没有来源概念、靠文件行位置标识条目"**——MxRun 用 `Source { provider, external_id }`

## 6. 逐类评估：留 / 改造 / 去掉

> 使用量口径：72 条的 `F` 值合计 **541**。**注意**：全局计数 `ShortCutRunCount=11595` 与 F 合计不符（可能中间重置过），所以 F 只能当**相对排序**用，不当绝对次数。

### 6.1 当时的第一个结论（**已被 §6.1.1 推翻，保留是为了记住教训**）

按 F 值排序时，榜单前 10 条看起来占了 **68% 的"使用量"**，另有 44% 的条目 F=0。
第一版分析据此写了"使用量极度集中""先把前 10 条跑通"等结论——**全是错的**，因为那些 F 值不是用户的使用记录。

**教训**：拿到一份"看起来像遥测数据"的字段时，先去源码里确认它是**谁写的、什么时候写的**，再拿它做决策。

（这一节的原始榜单含本机具体条目与次数，已移除；需要时看 `local/机器环境.md`。）

### 6.1.1 **推翻前面的 F 值分析**：绝大多数 F 是作者预置的模板权重（2026-09-13 查证）

`untShortCutMan.pas:1386-1467` 是"**文件不存在时写入默认清单**"的模板代码。把模板里每一项的预设权重与用户文件逐条比对：

| 条目 | 模板写死的权重 | 用户文件里的 F | 用户真实使用 |
|---|---|---|---|
| ie | 8 (`:1404`) | 8 | **0** |
| notepad | 7 (`:1405`) | 7 | **0** |
| cmd | 6 (`:1407`) | 6 | **0** |
| Calc | 5 (`:1408`) | 5 | **0** |
| Reg | 4 (`:1433`) | 4 | **0** |
| Recent | 10 (`:1445`) | 10 | **0** |
| b | 12 (`:1447`) | 12 | **0** |
| g | 14 (`:1448`) | 14 | **0** |
| zd | 9 (`:1450`) | 9 | **0** |
| Upgrade | 15 (`:1454`) | 15 | **0** |
| **r（运行）** | **100** (`:1461`) | **100** | **0** |
| cb | 12 (`:1462`) | 12 | **0** |
| cg | 24 (`:1463`) | 24 | **0** |
| ShowOnly / Hide / UnHide | 15 / 20 / 20 (`:1464-1466`) | 15 / 20 / 20 | **0** |
| **Computer（我的电脑）** | **100** (`:1401`) | **116** | **16 ← 唯一的真实增量** |

而且用户文件的**前 42 条（含 4 条分隔线）与模板逐条同序、同名、同值**，从第 43 条起才是用户自己加的。

**结论**：F 合计 541 里，**约 381 是作者预置的权重，只有约 160 是真实使用**（用户自己加的那些条目合计 144 + 模板里唯一被真正用过的一条 16 次）。

→ 因此 §6.1 那一版结论**作废**。真实的高频是**用户自己添加的应用**（具体清单与次数见 `local/机器环境.md`）。
→ 参数类（`运行` / 8 个搜索模板 / 窗口动作）**用户一次都没用过**——这反过来**强力支持 §7 把"应用自动发现"提到 P0、把参数机制降到 P1**。

**但这个排名是历史累计，不等于"现在还在用"——必须做口径校正（2026-09-13 补）：**

三份**活在变化的**数据与 F 对不上：

| 证据 | 内容 | 说明什么 |
|---|---|---|
| `FavoriteList.txt`（"关键字→条目"学习记录） | **完全没有 `r` / 运行 的痕迹**；里面出现的是用户真正在用的那些条目名 | 运行 的 100 次**不在这个文件的生命周期内**；且该文件含**已从快捷项里删掉的条目** → 它是长期累积、不清理的 |
| `ALTRun.ini` 的 `[DEBUG] LatestList` | 最近执行的三项都是**应用类** | 近期实际用的是应用，没有参数类 |
| `ParamHistory.txt` = **0 字节** | 参数历史为空 | 近期**没有用过任何弹参数框的命令**（含 `运行` 与搜索引擎） |

→ **修正结论**：`运行` F100 更可能是**历史重度使用**（或曾长期占据"空输入回车执行第 1 项"的位置——若如此，它的使用记录会被记成空关键字，后来被别的条目覆盖，这正好解释了"F=100 却无 `r` 记录"）。**"运行是第二常用"这个判断不能直接采信，需要向用户确认。**（后来确认：确实不常用。）

### 6.2 逐类结论

| 类型 | 条数 | F 合计 | 结论 | 现代改造要点 |
|---|---|---|---|---|
| A 应用 | 34 | 158 (29%) | **留，但换实现方式** | 自动发现（开始菜单 + UWP + App Paths）；手工只记带参数的例外（客户端要加命令行开关的、脚本型） |

### 6.5 F 值到底是什么（2026-09-13 查证）

> 起因：用户提问"`运行` 这么高频，是不是 AltRun 内部靠它实现某些功能刷出来的？"
> 结论：**不是内部刷的**——但它确实不能当"现在的习惯"用。

**查证 1：`Inc(Freq)` 全源码只有一个点**（`untShortCutMan.pas:2075`，在 `Execute(item, keyword)` 这个重载里）。哪些路径会计数：

| **会计数**（走带 keyword 的重载） | **不计数**（走无 keyword 的重载） |
|---|---|
| 主列表执行：回车 / 空格 / 双击 / 中键（`frmALTRun.pas:731`） | **第三热键"执行最近一项"**（`:2405`） |
| Ctrl/Alt+数字直接执行（`:1580`、`:1582`、`:1603`、`:1605`） | 管理器与编辑框的"测试"按钮（`frmInvalid.pas:89`、`frmShortCut.pas:214`） |
| "上一次列表"复用：输入以数字/空格结尾（`:1430`、`:1444`、`:1461`） | 内部 `Execute(cmdobj)`（`:840`） |

→ **程序内部没有任何"偷偷执行快捷项并计数"的通道**。F 确实是被用户操作累加出来的。

**查证 2：F 的存取往返是干净的**（排除了"串位 / 被写坏"的怀疑）：Freq 经由 ListView 的 `Data` 指针往返（`FillListView` 写 `Freq → Data`；`LoadFromListView` 读 `Data → Freq`），管理器中**新增的行不设 `Data`（=0，语义正确）**、分隔行也不设（Freq 本就无意义）；唯一的 `LoadFromListView` 调用点（`frmALTRun.pas:950`）位于 `with ShortCutManForm do` 作用域内，取的是**管理器自己的**列表——语义正确。

**查证 3：真正的原因是"永久累计 + 永不衰减"**。AltRun 的排序公式是

```
Rank := 1024 + Freq * 4 - 上次Rank * 128 - (关键字长度差) * 16      // untShortCutMan.pas:1026
```

**Freq 只增不减，且没有任何时间衰减。** 所以"早年用得多、现在早不用"的条目会**永远**排在高位。结合三份活数据（`FavoriteList` 无 `运行` 痕迹、`ParamHistory.txt` 0 字节、`LatestList` 全是应用类），可判定：**`运行` 的 F100 是历史积累，不代表现在的习惯。**

**给 MxRun 的结论（重要，直接影响导入器）**：

- **不要把 F 直接灌成 frecency 初值**——那等于把一个十几年的、不衰减的旧习惯模型搬进来，"我的电脑永远排第一"这类问题会一并继承。
- 建议：**不灌**（全部从 0 开始，让真实使用重建），或最多灌一个**会快速衰减的弱初值**（例如 `count = min(F, 10)` 且 `last_used = 导入时刻`，两周内自然淡出）。
- MxRun 现有的 frecency（频率 × 14 天半衰期）方向本来就是对的——**它正好是 AltRun 这个排序缺陷的解药**。

### 6.6 分隔线（`scBlank`）有什么用：**在启动器里完全没用**（2026-09-13 查证）

> 起因：用户提问"分隔线有啥用，为啥有专门的类目？"
> 结论：它是**作者默认模板里的分组标记**，而且**在启动器界面里根本不会显示**。

| 环节 | 代码 | 结果 |
|---|---|---|
| 排序 | `Sort`（`:1903-1925`）只把 `scItem` 放进 `m_SortedShortCutList` | **分隔线进不了"空输入时的全部列表"** |
| 搜索 | `FilterKeyWord:990` —— 非 `scItem` 直接 `Continue` | 搜索时跳过 |
| 执行 | `Execute:682` —— 非 `scItem` 直接 `Exit` | 点了也不执行 |
| 管理器的表格 | `FillListView:909-917` 给空行加一行空白 | **唯一能看见它们的地方** |

补充两点：

- 用户文件里"**第 77 行的空行不是分隔线**"，只是文件末尾的换行符（`WriteLn` 的产物）。真正的模板分隔线只有 **4 条**（`:1441`、`:1446`、`:1453`、`:1456`），位置与用户文件逐条吻合。
- 这 4 条**不是用户加的**：它们由默认清单模板写入（见 §6.1.1），用户文件的前 42 条与模板完全一致。

**给 MxRun 的结论**：

- **不要"分隔线"这个类目**——它是个"只在管理器里可见"的编辑期标记，连原版自己都不在结果列表里显示。
- 导入时**直接跳过空行**，不产生空条目。
- 将来若真需要分组，正确做法是**运行时按来源/类型自动分区**（现代启动器的 section header），而不是让用户在数据里手工插空行——手工插的行会占结果位、可能被搜索命中、还要被编号，而且得手工维护。

## 9. 前瞻需求：输入 `@` → 调用 `es.exe`（Everything）搜文件

> 用户 2026-09-13 提出：在输入框里打 `@` 就调用 Everything 的命令行客户端 `es.exe` 搜索目录/文件，结果能"打开 / 打开所在目录 / 执行"。
> 这是**查询型 provider**（现代启动器的标准形态：Raycast 的 Search Files、Alfred 的 find、PowerToys Run 的文件搜索），**不是一条"命令条目"**，所以不能靠导入实现。

### 9.1 它对架构的硬性要求（**必须 P0-1 就留好缝，否则以后要拆管线重做**）

| # | 要求 | 为什么现在就要定 |
|---|---|---|
| 1 | **Provider 分两类**：`Index`（启动时建索引、内存打分）与 `Query`（输入时按需查询、**异步 + 可取消 + 有超时**） | P0-1 定义 provider 接口时就要写进去；现在的结果管线是"一份内存数组打分"，没有异步位置 |
| 2 | **结果管线支持多来源**：静态条目（瞬时）+ 查询结果（后到）共存、可替换、可取消 | 否则 Everything 结果没地方进 |
| 3 | **瞬时条目**（不进库）：Everything 结果不落库，用临时 id（如 `everything:<完整路径>`） | 现在 `items` 全部来自数据库快照，没有"临时条目"概念 |
| 4 | **多动作**（一个条目多个动作） | 文件结果需要：打开 / 打开所在目录 / 复制路径 /（exe 时）以管理员运行 → **这是必须做多动作的直接理由** |
| 5 | **前缀注册表**：`@` → 某 provider。`@` 是**模式切换**，不是关键字 | 要可配置；且只在**输入开头**生效（出现在中间当普通字符） |
| 6 | **图标缓存要加上限 + LRU** | 文件搜索会灌进大量新路径，现在按 path 缓存且**无上限** → 内存会涨 |
| 7 | **异步 + 防抖 + 取消 + 条数上限** | 每敲一个字符起一个 `es.exe` 必然卡；需防抖（~150ms）、限制返回（如 30 条）、取消上一次查询 |
| 8 | **配置项**：`es.exe` 路径、结果上限、防抖时长、前缀字符 | 放 `cfg:` 表（现有 `get_config`/`set_config` 即可） |

### 9.2 必须避开的坑（免得重踩）

- **不能在 UI 线程等结果**：MxRun 空闲时不跑 `ui()`，所以查询结果回来必须 `ctx.request_repaint()`，否则界面不刷新（既有踩坑记录第 1 条）
- **`es.exe` 输出编码**：中文 Windows 下输出可能是 GBK/控制台代码页，按 UTF-8 直接读会乱码 → 必须显式处理
- **三种失败要分开提示**：① 没装 `es.exe` ② Everything 没在运行 ③ 查询确实无结果——不能都显示"没结果"
- **`es.exe` vs Everything IPC**：每次查询起一个进程有开销（约 20–60ms）。Everything 本身提供 IPC（`WM_COPYDATA`）和官方 SDK，可做到毫秒级、不起进程。**建议先用 `es.exe`**（简单、够快、零依赖），但把 provider 实现做成**可替换**，将来换 IPC/SDK 不动上层
- **结果条数上限**：Everything 可能返回几十万条，必须用 `-n` 限制并只取前 N 条

### 9.3 对优先级的影响

**不改变 P0 的顺序**（它不阻塞 `模型 → 执行器 → 导入器 → 应用自动发现`），但它**改变 P0-1 的一个设计决定**：

> **provider 接口从第一天起就必须支持"查询型"**（异步/可取消/超时），并且**多动作（每个条目一个动作列表）必须现在就做**——不能等以后再加。

实现这个功能本身单列为后续工作包（见 `开发进度.md` §3 的后续表）。
