## 2. 已验证的事实（都有实测证据，别再重新怀疑）

### 2.1 性能（README「性能实测」节有完整表格）

| 指标 | 实测 | 备注 |
|---|---|---|
| 热键按下 → 首帧渲染 | **1.2–5.9 ms**（p50 ~3.7ms） | 设计预算 50ms，余量一个数量级；59 条数据下复测仍是 **2.5–3.9 ms** ✅ |
| 私有提交（常驻，与显隐无关） | **~106–157 MB** | 真实占用看这个 |
| 工作集（显示中） | ~130–270 MB | 含 GPU 映射 |
| 工作集（隐藏数小时后） | ~11 MB | **只是系统 trim 的结果，不是真实占用** |
| 线程 | 27 | glow 后端 |
| 冷启动 → 首帧 | **~255–295 ms**（59 条数据） | 拆解：eframe/GL/字体初始化占掉绝大部分，**我们自己的数据只花 0 ms** |
| 冷启动 → 图标齐 | **~430–450 ms** | 首帧后 ~175 ms 内补齐可见行的图标（emoji 先顶上） |

**图标加载在 2026-09-14 重做过（原来是冷启动最大的开销）**：

- 老做法：启动时**阻塞预热全部**图标，再显示窗口。实测 **6 条 49–67 ms → 59 条 544–770 ms**（线性增长）。也就是冷启动约 `250 ms(框架) + 600 ms(图标) ≈ 850 ms`，而且**条目越多越慢**——正是"后面越来越多会卡顿"的那条路。
- 新做法：**按需 + 后台 + 有上限缓存**（`Icons`）。索引建完就出窗口（0 ms），行渲染时才请求自己那一行的图标，worker 线程取像素，UI 帧里上传纹理；缓存上限 256（顺带修掉"缓存无上限"那条欠账，对将来的文件搜索很关键）。
- 附带：`main` 里还起了个短命线程，在 eframe 初始化期间**提前把 shell 映像子系统预热掉**（首次 `IShellItemImageFactory` 调用要 ~145 ms，实测降到 ~122 ms、图标就绪提前约 40 ms）。
- 实测时间线（3 次冷启动）：`first frame 251/255/260 ms` → `worker first fetch 122–124 ms` → `全部可见图标 ~440–450 ms`。

**渲染后端 = glow(OpenGL)**，不是 eframe 默认。对比 wgpu：提交 464MB / 55 线程 / 881 句柄，画面逐像素一致。`MXRUN_RENDERER=wgpu` 是退路。

### 2.2 系统材质（E2）

- **Acrylic 可达**：`DwmSetWindowAttribute(hwnd, DWMWA_SYSTEMBACKDROP_TYPE, 3)` 在 egui/glow 的透明无边框置顶窗口上工作正常，能把背后内容（含其他窗口）糊成柔和色块。不需要换 WinUI。
- **Mica 不适合做启动器材质**：`DWMSBT_MAINWINDOW` 只采样壁纸、刻意不显示背后窗口，深色壁纸区域表现为死平暗色（实测像素恒定 `30,32,37`）。
- 开关（默认 off）：`MXRUN_BACKDROP=acrylic|mica|off|<n>`、`MXRUN_CARD_ALPHA=0-255`。
- **待处理**：材质会填满整个窗口矩形，现在"靠透明角做圆角"的做法会失效，圆角要改用 `DWMWA_WINDOW_CORNER_PREFERENCE`。

### 2.5 P0-1 命令模型落地（2026-09-13 完成并实测）

- **新模型**（定义在 `src/store.rs`，设计见 `命令模型设计.md` §4）：
  - 条目 = 标题 / 副标题 / **触发词（多值）** / **动作列表** / 参数规格 / 启动方式 / **来源** / 健康
  - 动作效果是**封闭集合**：打开 / 运行 / 内建 / 复制 / 定位（加能力就加动词，不加类型）
  - 参数规格 = **来源 + 编码 + 插入方式**三件独立的事（不再是一个枚举兼职四职）
  - 来源 = `provider + external_id`（导入幂等、识别"源里删了"、多来源互不干扰）
- **迁移安全**（三条一起做）：
  1. 所有结构 `#[serde(default)]` → 老记录仍能反序列化
  2. 迁移由 meta 的 **`schema_version`** 驱动（缺失 = v1）；迁移**只在版本落后时**跑（因为 v1 记录在加了默认值后会"成功解析成空条目"，这是个陷阱）
  3. **坏记录不再静默丢弃** → 写进 `Store::warnings`，再由 `main` 写 `mxrun.log`；**id 保持不变**（frecency 按 id 存，变了统计就脱钩）
- **实测验证**（用**真实库的副本** + 独立 `APPDATA` 跑，不动真库）：
  - 首次启动：`store: migrate: v1 -> v2, 6 条已转换`

  - `backups/` 每次启动留一份，实测 2 份
- **搜索**：触发词进入搜索池并**加权**（精确 1000 / 前缀 400 / 包含 200）
  - 修掉了 v1 的老毛病：索引只拼 `name + desc`，关键字（`myip` 这种）**永远搜不到**
- **测试**：`cargo test` **12 项全过**（含"关键词命中压过模糊标题命中""只靠关键词也能搜到""三级权重顺序""旧库迁移保留 id""坏记录被上报""重复导入不产生重复"）

### 2.6 P0-2 执行器（2026-09-13 完成并实测）

新增 `src/exec.rs`，`run(item, action)` 分派五种效果：

| 效果 | 调用 | 为什么是它 |
|---|---|---|
| `Open` | `ShellExecuteW` | 只有它能认文档/目录/网址/协议/CLSID/`.msc`/`.cpl`——这些都不是可执行文件 |
| `Run` | `CreateProcessW` | **带参数的命令行不是一个文件名**。AltRun 把整串交给 `ShellExecute`，只因后面那个 `WinExec` 兜底才没露馅（`untShortCutMan.pas:341-350`）；按效果拆开就没有这个陷阱 |
| `Builtin` | 进程内 Win32 | 显示桌面 = 给 `Shell_TrayWnd` 发 `MIN_ALL`(419)；隐藏/恢复 = `ShowWindow`；关机/重启 = `shutdown /s|/r /t 5`。**不引入外部 exe**。⚠️ **恢复窗口必须用"上一次被隐藏的那个句柄"**，不能用当前快照——等用户再次呼出时，前台窗口早已换成他刚点的那个了（AltRun 的 `WinCtl.exe UnHide` 不带参数也是这个原因） |
| `Reveal` | `explorer.exe /select,"…"` | |
| `Copy` | 剪贴板 | |

**参数机制落地**（`ArgSpec` 那三件事）：

- **编码**：原样 / URL / UTF-8。后两者在 Rust 里都是 UTF-8 百分号编码——AltRun 的差别只源于 Delphi 从 ANSI 字节编，现代化后两者等价（数据字段保留，行为统一）
- **插入**：`Replace` 会填 `{p}` / `%p` / `{%c}` 中出现的任何一种（AltRun 只替换**第一个**）；`Append` 追加到末尾——**搜索引擎就是靠它**
- **来源**：剪贴板、前台窗口（句柄/标题/类名）今天可用；**`Prompt` 没有界面 → 返回 `NeedsInput`**
- **前台窗口快照必须在呼出前取**（`show_window` 里调 `remember_foreground`）。否则"前台窗口"就是 MxRun 自己——AltRun 也是在热键按下瞬间取的值（规格 §4）

**`*` 标记（用户选的 C 方案）**：需要输入参数的条目，副标题显示「需要输入 *」；按回车不执行，而是提示"输入功能在下一步加入"。这样导入后不会让人以为程序坏了。

**顺带修掉两个图标缺口**（样本档案一跑就暴露，导入数据里全是这类）：

1. `%WINDIR%` / `%PROGRAMFILES%` 这类**环境变量目标**：图标解析前先展开
2. **裸名与带参数命令**：按 `PATHEXT` 在 PATH 里补扩展名解析——`nslookup`、`cmd /k %p`、`shutdown /s /t 5` 以前都取不到图标

实测：样本档案图标 **4/13 → 7/13**（剩下 3 条网址 + 2 条内建动作本来就没有文件图标）。

**测试**：`cargo test` **25 项**（新增 13 项）。其中两项是**真的动了系统**的端到端测试：

- **真实窗口的隐藏/恢复**：真起 notepad → 按应用的方式快照前台窗口 → 用执行器自己的动词隐藏 → 用 Win32 `IsWindowVisible` 校验 → 恢复 → 杀掉。**而且它是安全的**：如果前台窗口不是 notepad（比如是你的终端），它会**跳过而不是失败**——绝不会去隐藏别的窗口

### 2.7 P0-3 导入器（2026-09-13 完成并实测）

新增 `src/import.rs` + `--import` 开关（GUI 程序没有控制台，所以结果既写 `mxrun.log`，也弹一个汇总框）。

**用真实文件实测**（2026-09-14 已代为导入到真实数据目录 `%APPDATA%\MxRun`）：

```
import: lines=76 commands=72 imported=59 needs_input=4 builtin=4 removed_seed=6 skipped(sep=4 unwanted=13 unsupported=0)
icons: 47/59 resolved
```

**导入会自动清掉演示数据**（`removed_seed=6`）：新库的种子条目 provider 是 `seed`，而 v1 老库迁移出来的是 `legacy`——两种都要删，否则列表里会出现"计算器"和导入的 `Calc` 并存这类重复。判断依据写在 `DEMO_PROVIDERS` 常量里，注释说明了为什么 `legacy` 也一定是演示数据（v1 的 `add_command` 从未被调用过，用户不可能加过自己的命令）。

**踩到的坑（值得记）**：第一版只按 `provider == "seed"` 删，结果真实库 `removed_seed=0`——因为用户那 6 条是老格式迁移来的（`legacy`）。单元测试当时用的是新库（`seed`），没能覆盖这条路径；现在测试会先把 provider 改成 `legacy` 再验。

**两条不照抄的规则**（都在代码里，`--import-all` 可关掉）：

1. **不灌 `F<n>` 权重** —— 那是作者模板里的预置值（§6.1.1），灌进来等于把一个十几年前、不衰减的排序冻进 frecency
2. **`@.\WinCtl.exe …` 映射成内建动词**（显示桌面 / 只显示当前窗口 / 隐藏 / 恢复），并**丢掉那个 `@` 前缀**（它原本只是"别让助手 exe 闪窗口"）

**跳过 13 条**：12 条无用条目（IE、Internet 控制、添加删除程序、系统属性、`%WINDIR%`/System32/ProgramFiles 三个目录、`.\ALTRun.ini`、升级死链、搜狗MP3、VeryCD、Yahoo）+ **1 条用户明确不要的**：`cmd`（Dos窗口，`cmd /k %p` —— 一个先弹框问你"要运行什么"的条目，用户 2026-09-13 确认不会用到）。

**关键实现细节**：

- **编码**：文件是 GBK（Delphi 写的是 ANSI 代码页）。用 Win32 `MultiByteToWideChar(CP_ACP)` 解码，**不引入新依赖**（已在用 `windows` crate）；UTF-8 文件也照样读
- **命令行里含 `|`**：只 `splitn(5, '|')`，第五列保留原样（URL 里可能有 `|`）
- **打开还是运行**：URL/`::`/`shell:`/`ms-settings:` → 打开；**目标后面带参数 → 运行**（`cmd /k %p`、`shutdown /s /t 5`）；只有一个目标 → 打开
- **参数规格从数据推导**：`{%c}`→剪贴板、`{%wd}`→前台窗口、其余非空编码列→需要输入；有占位符→替换，没有→追加（搜索引擎的机制）

**实测查询**（用导入后的档案，自检开关）：

| 查询 | 结果 | 说明 |
|---|---|---|
| `stea` | **1 条**（目标应用） | 关键字前缀命中 |
| `cb` | **1 条**：百度 搜索剪贴板 | ⚠️ `needs_input=false` —— 见下面的 bug |
| `hide` | 2 条：隐藏本窗口 / 恢复窗口 | 两条都是内建动作，都合理 |
| `dos` | 8 条（Dos窗口 排第 1） | 关键字是 `cmd` 不是 `dos`，只能靠标题模糊匹配 → 噪音仍在 |

**顺带修掉的一个真 bug**：`wants_input()` 原本写成"输入来源 ≠ 无"，于是**剪贴板搜索（`cb`/`cg`）也会被标成"需要输入"**——但它们根本不用打字。改成只认 `Prompt`。单元测试当场抓住了它（`search_engines_append_and_clipboard_ones_replace`）。

**同批做的小改进：搜索分数闸门**（`SCORE_GATE = 0.15`）
低于最高分 15% 的结果不再显示。实测效果：`stea` 从一堆噪音变成 1 条、`cb` 1 条、`hide` 2 条。
**但注意**：闸门只在"有关键字命中"时有效（那是一个数量级的差距）；像 `dos` 这种只能靠标题模糊匹配的查询，分数都挤在 70~90 之间，闸门拦不住。要再干净就得动匹配算法（拼音那串长文本里子序列太多），属于后续调优。

### 2.9 启动次数统计 + 行内容补全（2026-09-14）

用户提出："每个项目的启动次数要统计，并显示在列表项里（现在列表项很空）"。

### 2.10 P1-1 输入机制（2026-09-15 完成，端到端实测）

用户拍板：**形态 = 顶框切换式**（不新开窗口），**参数历史 = 做**（存进 redb，不新增文件）。

**交互**（对齐 `AltRun交互规格.md` §3 的两段式，只是把 `frmParam` 从独立窗口搬进主窗口）：

| 步骤 | 行为 |
|---|---|
| 选中带参数的条目 → Enter/空格 | 顶框变成参数框：左边一个琥珀色小标签（`⌘ 百度搜索`），右边是输入框；列表换成该条目的参数历史 |
| 输入 | 每敲一字重算建议（子串匹配、忽略大小写）；**空格照常输入**（主框里空格是"执行"，这里不是） |
| ↑ / ↓ | 高亮历史项（高亮 ≠ 改写输入框内容）；回车执行**高亮项**，没高亮就执行**手输内容**，两者在底部提示行里写明 |
| 单击建议 | 填进输入框（不直接执行）——历史参数常常要改一下才用，原版下拉框也是这个行为 |
| 回车（空输入） | 不执行，留在输入态并提示（原版对话框同样拒绝） |
| Esc | 两级：先清空输入 → 空后再退回搜索（与主框、与原版 `frmParam` 都是同一套语义） |
| 窗口隐藏 | 提示一并丢弃（下次呼出是干净的搜索态） |

**落地的三件事**：

1. `exec::run_with_arg(item, action, Some(text))` 是新的执行入口；`run()` 退化成 `run_with_arg(…, None)`。`ArgSource::Prompt` 拿不到文本时仍然返回 `NeedsInput`——**而 `NeedsInput` 正是 UI 打开提示的信号**（执行器不认识 UI，UI 只认这一个返回值）
2. **参数历史存 meta 表**（键 `param:<条目 id>:<参数>`，值是使用次数）：按条目分开记（"我常开的那个 wiki 页"和"我常搜的词"不再抢同一个名额），上限 50（对齐原版 `ParamHistoryLimit`），超限丢使用次数最少的。**不新增文件**——原版是 exe 旁边的 `ParamHistory.txt`
3. `BuiltinVerb::RunInput`（原版「运行」）接上了：输入当命令行执行，`LaunchMode` 强制 Normal（条目自己的 Hidden 会让"运行我输的东西"看不见窗口，那不是本意）。⚠️ 目前**没有条目产生这个动词**，属预留能力（§3 P1-4 的"运行/兜底"还没做）

**实测证据（无键盘跑通全链路）**——用样本档案里新加的 `p11` 条目（`cmd /c echo {p} > "%TEMP%\mxrun-p11-param.txt"`，Hidden 启动，无窗口闪现）：

```
MXRUN_SELFTEST=p11 MXRUN_SELFTEST_EXEC=1 MXRUN_SELFTEST_PARAM=hello-param-11
→ selftest: query="p11" rows=1 · row0 needs_input=true
→ prompt: open for "参数写入文件" (history=0)
→ execute: 参数写入文件 (+parameter, 14 chars)
→ %TEMP%\mxrun-p11-param.txt 内容 = "hello-param-11"      ← 参数真的进了真实进程
第二次：history=1 suggestions=1（用过的参数被记住并出现在建议里）
第三次：history=1 suggestions=0（输入无关文字时建议被过滤掉）
```

**测试**：`cargo test` **51 项**（新增 11 项）。其中 `typed_parameter_reaches_a_real_process` 是**真起进程**的端到端测试：条目 `cmd /c echo {p} > <临时文件>`，先用 `run()` 断言必须 `NeedsInput`，再用 `run_with_arg(…, "hello-param")` 断言**文件里真有这串字**——这是我们自己的字符串处理之外、唯一能证明"参数没被吞掉"的证据。

**仍未验证的部分（诚实记一笔）**：跑在本机自动化环境里时窗口拿不到前台，`hide: lost focus` 会在 ~300ms 后把窗口收掉，而 GDI 截图**看不见这个窗口**（§7 踩坑 12）——所以**参数输入界面的实际画面与键盘手感（空格、↑↓、Esc 两级）没有机器证据**，需要人眼过一遍（三分钟，见 §9 第 6 条）。逻辑层面（状态机 / 过滤 / 编码 / 落库）都有单元测试与上面的真进程证据。

### 2.11 加项闭环：右键进得来、F2 改得动（2026-09-15 完成，双进程实测）

**背景**：在此之前 MxRun **一条加项入口都没有**——库里 59 条只能靠改 AltRun 的清单再 `--import`，
而"右键 → 发送到 → ALTRun"是用户用了十几年的习惯（`AltRun交互规格.md` §11 实测：本机 `SendTo\ALTRun.lnk` 存在、
`AddToSendTo=1`；原版的 shell 右键菜单是死代码、零调用点）。

**五个入口，一张卡片**（都落到同一个"小确认框"）：

| 入口 | 怎么触发 | 预填 |
|---|---|---|
| 发送到 | 右键文件 → 发送到 → MxRun | 由路径推导（见下） |
| 右键菜单 | 文件 / 目录 / 目录空白处 → "用 MxRun 添加(&M)" | 同上 |
| 命令行 | `MxRun.exe "<路径>"`（也支持拖一堆文件到 exe 上） | 同上，多选排成队列 |
| 托盘"新建条目…" | 托盘右键菜单 | 三个框全空 |
| 无匹配回车 | 输入一个搜不到的词直接回车（原版"无此项，添加它?"） | 关键字/名称 = 输入的词，命令行留空 |

**预填规则照原版 `frmShortCut`**（`untShortCutMan.pas:799-882`）：`.lnk` 先解析到真实目标
（两种例外保留 lnk 本身：解析不出来、目标落在 `%windir%\Installer\` 的 MSI 图标 exe）；
**关键字 = 文件名去扩展名，目录不切**（`node.js` 不能变成 `node`）；URL 取主机名；
名称 = 关键字；命令行 = 完整路径。

**"不打扰"是这套交互的灵魂**（原版两种情况下都**不显示主窗口**，只弹一个小框）：

- 第二个实例**只写一个请求文件就静默退出**——不弹"已经在运行"，也不显示主窗口
- 运行中的实例由**后台线程**每 100ms 收一次（它本来就在为热键/托盘轮询），然后把窗口**按卡片尺寸**显示出来
- 也就是说：请求到达时窗口还没出现，出现时就已经是小卡片了，**不会先闪一下主列表**
- 卡片里改完 → 回车 → 落库 → 窗口直接收起，回到 Explorer

**为什么用文件而不是窗口消息**：AltRun 给已有窗口发 `WM_SETTEXT`，而 eframe/winit 不给我们接收任意窗口消息的入口
（事件循环在 winit 手里）。通道是 `%APPDATA%\MxRun\inbox\` 目录：写临时名再 `rename`（读者永远看不到半截文件）、
读完即删、空文件 = "只是唤醒"（等于用户又双击了一次 exe，原版这里是弹"已经在运行"）。
副作用是**顺手修掉了原版的一个缺陷**：原版加项路径绕过单实例检查，两个实例可能同时写列表文件；MxRun 走交接，只有一个写者。

**落库**：`provider = "manual"`，`external_id` = 小写化的原路径 → **同一个文件再加一次是"更新"而不是"新增"**，
启动次数跟着走。F2 编辑则保持原 id 与来源（不碰 `arg` 规格、启动方式、多触发词里的第 2 个以后）。
关键字撞车时：**第一次回车只警告**（"已被「记事本」使用 —— 再按一次回车将覆盖它"），**第二次才覆盖**——
原版是弹模态问一句，这里把同一个问题变成一次按键，符合它"确认框必需但别啰嗦"的意图。

**F2 的归属**：原版 F2 = 编辑当前项，MxRun 之前拿 F2 当设置页 → **按原版对齐**：F2 = 编辑，
设置移到托盘菜单（原版也把"配置"放在托盘菜单里，还带 `Alt+C`）。托盘菜单同时新增"新建条目…"。

**入口注册是显式按钮**（设置页两行 + `--install-integration` / `--uninstall-integration` 开关），
**不在启动时偷偷写**：写 `SendTo` 与注册表是对用户系统的可见改动，该由他点一下。
右键菜单写在 `HKCU\Software\Classes\{*|Directory|Directory\Background}\shell\MxRun`（**免管理员**；
原版写的 `HKCR` 且从未被调用）。

**实测证据**（全部无键盘，用临时档案跑，真实数据没动）：

```
① 交接链路（两个进程）
   B: handoff: sent 1 path(s) to the running instance (…inbox\req-…txt)   ← B 退出码 0、没窗口
   A: handoff: received 1 path(s) → add: open for "…\My Test Tool.exe"
   A: add: created "My Test Tool" -> …\My Test Tool.exe      status="已添加：My Test Tool"
   inbox 目录剩余文件数 = 0（读完即删）
② 关键字撞车
   attempt 1 → 卡片仍开着：关键字「notepad」已被「记事本」使用 —— 再按一次回车将覆盖它
   attempt 2 → add: replaced "notepad" -> C:\Windows\System32\notepad.exe → index: 7 items
③ F2 编辑（`MXRUN_SELFTEST_EDIT=1`）
   selftest: editing "记事本" (id=seed-1, launches=1)
   add: updated "notepad" -> notepad.exe --mxrun-selftest
   after edit: id=seed-1 title="记事本" command=Some("notepad.exe --mxrun-selftest")   ← id 没变 = 启动次数没丢
④ 注册表 / SendTo 实际产物（装完检查后已卸载干净）
   HKCU\Software\Classes\*\shell\MxRun  (Default)=用 MxRun 添加(&M)  Icon=<exe>
   …\command (Default)="<exe>" "%1"     Directory 同；Directory\Background 用 "%V"
   SendTo\MxRun.lnk → target = <exe>（935 字节）

```

**三种"当时它在不在跑"的情况都实测过**：

| 情况 | 行为 | 实测 |
|---|---|---|
| **MxRun 正在跑（显示或隐藏都算）** | 第二个实例把路径写进 inbox 后静默退出；主实例把窗口**按卡片尺寸**显示出来 | 隐藏状态下的验证：日志先 `hide: lost focus`（被 notepad 抢走前台），3 秒后 `handoff: received` → `add: open` → `add: created` → `add: done, hiding`。**卡片能被收下就说明窗口确实被重新显示并出帧了**（收件逻辑跑在 `ui()` 里，隐藏的窗口不出帧） |
| **MxRun 没在跑** | 自己启动（约 250ms）→ **窗口直接以小卡片出生**（viewport 就按卡片尺寸创建，不会先闪一下主列表）→ 确认后落库并收起 | `instances before: 0` → 加完 `instances after: 1`；随后用自检查询确认条目真的在库里：`row0 title="No Run Test" category=应用 score=550.0` |
| **加完 / 放弃之后** | 窗口收起，**进程留在托盘常驻**（热键可用）。⚠️ 与原版不同：原版"没有实例则自己加载后添加**再退出**"——**用户 2026-09-16 拍板：保持常驻，但给个提示**（见下） | `add: done, hiding`；进程数 1 |

**"常驻提示"**（用户拍板的折中，2026-09-16）：只有当**这次加项本身就是 MxRun 的第一次启动**时
（`cold_start_add`），卡片确认后窗口**不立刻消失**，而是原地显示一条 2.6 秒的绿字提示
「已添加：X ／ MxRun 已在托盘运行（Alt+F1 呼出 · 右键托盘图标可退出）」，然后自己收起——
让用户知道"刚才那一下顺带启动了一个后台进程"。Esc 或回车可以提前关掉它。
交接进来的加项（MxRun 本来就在跑）**没有这条提示**：用户已经知道它在跑，没必要多话。
`tray-icon` 0.25 没有气泡通知 API（只有 tooltip），所以提示做在自己的窗口里——反正按回车时用户正看着它。

实测（临时档案，无键盘）：`instances before: 0` → `add: created "Toast Test"` →

**窗口一隐藏，卡片就丢掉**（与参数提示一致）：卡片通常来自一次"右键"，用户注意力早走了——留着它会让下次按热键时迎面撞上一个半填的表单；预填是免费的，重新右键一次就有。

**测试**：`cargo test` **67 项**（新增 16 项：`ipc` 5 项交接/垃圾文件/并发、`integrate` 6 项路径推导与

### 2.12 便携化与自愈（2026-09-16 完成，实测）

**起因（用户提问）**："这个项目最终是做成便携版的话，这个加项的功能要怎么添加到一台没有下载安装过 mxrun 的电脑？"
——当时那套集成有两个漏洞：路径写死成**绝对路径**（换机器/换盘/改目录名就断），"要不要集成"这个意图又只存在 `%APPDATA%`（每台机器一份，不跟着便携文件夹走）。

**三件事一起做**：

| # | 做什么 | 怎么做的 |
|---|---|---|
| 1 | **便携数据模式** | exe 旁边放一个空的 `portable.txt` → 数据库、备份、日志、交接收件箱全在 `data\` 里（`store::default_data_dir` 一处判定，`log_line` 也跟着走）。整个文件夹随便拷，配置与"右键集成是我的"这个事实一起跟着走 |
| 2 | **启动自愈** | **注册本身就是意图记录**，不另存开关：启动时如果"注册存在，但不是指向我" → 静默重写（`repair_if_registered`）。所以文件夹改名/换盘符后**跑一次就自动修好**；而"什么都没注册"不会被当成疏漏（那是用户的选择），绝不擅自添加 |
| 3 | **首次运行问一次** | 只有当"这台机器上什么都没注册"且"没问过"时才弹一张卡片问要不要加入右键。标记写在 `%LOCALAPPDATA%\MxRun\integration-asked`——**故意不放在数据目录**：便携目录会跟着走，而"这台机器的资源管理器认不认识 MxRun"是**机器本地事实**。答"加入"或"不用了"都算答过，不再追问；窗口被隐藏则算"以后再说"（不写标记，下次再问） |

**新机器上的完整体验**：把文件夹拷过去 → 双击 `mxrun.exe` → 问一次"要不要加进右键菜单" → 选"加入" → 以后每次启动自动把路径校准到当前副本。

**实测（全部临时目录，跑完已清理；你机器上的注册已还原成指向 `target\release\mxrun.exe`）**：

```
① 便携模式：<portable>\mxrun.exe + portable.txt →
   日志 startup: data_dir=…\mxrun-portable-A\data portable=true
   目录内容：data\mxrun.log、data\mxrun.redb；而伪造的 %APPDATA% 里"什么都没有"
② 自愈：把 mxrun-portable-A 整个改名成 -B →
   移动后注册表仍指向 A（这就是原来会断的样子）
   跑一次 B\mxrun.exe → self-heal: 发送到 已重新指向 …\mxrun-portable-B\mxrun.exe
                        self-heal: 右键菜单 3 处已重新指向 …\mxrun-portable-B\mxrun.exe
③ 首次询问：先卸干净（模拟新机器）→ 启动 → integration: nothing registered on this machine, asking
   →（脚本代答 yes）→ 已加入右键菜单（3 处）和「发送到」→ 注册表与 SendTo 都指向 B
```

**顺带说明（也是坑）**：便携副本与 `%APPDATA%` 正式版各自一个数据库（启动次数、参数历史分开算），
而**单实例互斥体是全局的**——两个一起跑会互相顶掉。同一台机器上建议只留一个。

**给用户的加项通道优先级**（便携场景下不进系统也能用）：
拖文件到 `mxrun.exe` 上（支持多选排队）→ `MxRun.exe "<路径>"` → 搜索无匹配回车添加。
**系统集成是"可选加强"，不是加项的前提。**

**调试开关**：`MXRUN_SELFTEST_INTEGRATION=yes|no` 无键盘回答首次询问（只用于脚本验收）。

### 2.13 删除 + 快捷项管理（2026-09-17 完成，实测）

**背景**：在这之前能加、能改，**但删不掉**，也没有一个"把条目都列出来看看"的地方（列表只在搜索时出现）。
原版对应的是 `Delete` 键 + 托盘"快捷项管理"（`frmShortCutMan`，四列：ShortCut / Name / Param Type / Command Line）。

**三个入口**：

| 入口 | 行为 |
|---|---|
| 列表/管理器里按 `Delete` | 第一次按**只问**（状态行："再按一次 Delete 删除「X」（其它按键取消）"，行变红），第二次才删。原版是弹模态确认框（`frmALTRun.pas:2233-2241`）——**问题一样，只是不要那个框**，比照加项卡片"关键字撞车"的处理 |
| 行右键菜单 | 编辑 / 删除 / 打开所在目录（原版列表右键是"添加/编辑/删除/-/打开所在目录"，"添加"仍在 Insert 与托盘上） |
| 托盘 → **快捷项管理…** | 打开管理视图（原版托盘菜单第二项就是它，还带 `Alt+S`） |

**管理视图**（同一个窗口、换一种列表，尺寸放宽到 880×560——原版给命令列留了 400px，同样的理由）：

- **显示全部条目**（不走分数闸门、不受 8 行上限约束，改用滚动条），默认**按启动次数排序**、次数相同的按标题——"没启动过的一堆"自然沉在底部，正是收拾东西时要找的
- 顶部筛选框就是熟悉的搜索框（同一套匹配），筛 59 条和平时搜索手感一致
- 键位照原版：`F2` 编辑、`Insert` 新建、`Delete` 删除、**双击编辑**（管理器里没有"执行"这回事，所以回车也做成编辑）

**存储层的两件事**（这是"删除"能站得住脚的关键）：

1. **删除会连带清掉统计**：`frec:<id>` 与 `param:<id>:*` 一起删。它们按 id 存，留着会让后来恰好复用同一 id 的条目"继承"被删条目的次数
2. **墓碑（tombstone）**：给 `(provider, external_id)` 记一条 `gone:` 键。没有它，"删除"对导入条目就是**谎话**——下次 `--import` 会原样搬回来。导入器现在跳过并计入 `skipped_deleted`，汇总框会写"你在 MxRun 里删过的 N 条没有再加回来"。
   **但"手动再加一次"会清掉墓碑**：导入不该复活被删的东西，而用户主动添加是改变主意，不是复活（`clear_deleted`）。
   顺带留了 `deleted_sources()`，"已删除 / 撤销"列表以后可以直接用它。

**实测（临时档案；导入 → 删除 → 再导入，全程无键盘）**：

```

   manage: open (6 items) → selftest: manage rows=6 items=6
   delete: confirm? "Bing"            → 状态="再按一次 Delete 删除「Bing」（其它按键取消）"
   delete: removed "Bing" (id=seed-4, provider=seed) → index: 5 items → 状态="已删除：Bing"
② 墓碑真的挡住重新导入
   第一次 --import：lines=2 imported=2 removed_seed=6
   管理器里删掉 BBB Tool（id=shortcutlist:line:2）
   第二次 --import：import: 跳过你删过的条目：BBB Tool
                    lines=2 imported=1 … deleted=1        ← 没回来
```

**测试**：`cargo test` **71 项**（新增 3 项：删除连带清统计 + 墓碑 + 主动添加清墓碑；删演示条目不留墓碑；导入跳过被删条目）。

**调试开关**：`MXRUN_SELFTEST_MANAGE=1` 打开管理器、`MXRUN_SELFTEST_DELETE=1` 顺手把选中项删掉（**真删**，只对临时档案用）。

**仍要人眼确认**：管理器那一屏的排版（四列挤不挤）、`Delete` 两步的手感、右键菜单里的三项。

### 2.14 应用自动发现（P0-4，2026-09-17 完成，实测）

**用户拍板**：只做开始菜单（UWP 留到以后）、跳过网页快捷方式、**默认开**。

**先量了再动手**（这台机器）：开始菜单 **193 条**（175 `.lnk` + 18 `.url`；用户 56 / 公共 137），
解析一个 `.lnk` 到真实目标 **1.77 ms**（COM 往返），全扫 ≈300 ms；`shell:AppsFolder` 枚举 **672 ms / 217 项**，
但其中 **174 项是桌面应用**（和开始菜单同一批，只是换了个更慢的入口）、只有 **43 项是 UWP 形态**
（AUMID 含 `!`：设置/邮件/日历/地图/便笺/Teams…），而且 **`Path` 属性给的是 AUMID 不是 exe 路径** ——
所以 UWP 只能按名字去重，正是文档警告的不可靠那种。**结论：一期只扫开始菜单**（能按真实 exe 路径去重），UWP 以后单独做。

**性能（这是问题的核心）**：

| 指标 | 结果 |
|---|---|
| 冷启动 → 首帧 | **256 ms（与之前 255ms 持平）** —— 扫描在**首帧之后**才启动 |
| 首帧之后的后台扫描 | **180 ms**（107 个快捷方式过 COM），完全看不见 |
| 第二次启动（增量） | `seen=0 cached=107` —— **一次 COM 都不调**，145 ms（就是走目录 + stat） |
| 索引重建 | **100 条 0 ms**（59 → 100 条毫无感觉） |
| 呼出延迟 / 搜索 | 不变（扫描线程不碰 UI，也不碰数据库） |

**三个关键设计**：

1. **扫描线程不碰数据库**：redb 对文件**独占加锁**，worker 里再开一个 `Store` 会直接失败
   （实测 `另一个程序已锁定文件的一部分 (os error 33)`）。所以拆成
   `read_input`（UI 线程读快照：已知目标路径 + 扫描缓存，各一次查询）→
   `collect`（worker：只做文件系统 + COM）→ `apply`（UI 线程：一次事务写库）。
   顺带的好处：扫描逻辑可以脱库测试。
2. **增量缓存**：每个快捷方式按 `(路径, mtime, 大小)` 记在 `scan:` 键下，没变过就**连 COM 都不调**。
   缓存值里带一个 `SCAN_GEN`（过滤规则变了就 +1），规则升级时自动全量重扫。
3. **去重按解析后的 exe 路径**（文档反复强调的坑）：你手工的 `chrome` 和扫出来的 "Google Chrome"
   是同一个 `chrome.exe`，只留你那条。实测 `existing=7` —— 正好是演示条目里的
   calc/notepad/cmd/explorer 那几条被认出来。

**过滤规则**（用户要求"再激进一点"，实测在这台机器上滤掉 30 条）：
- **`.url` 网页快捷方式全跳过**（18 条）
- 名字过滤分三类：**前缀**（`uninstall`/`unins`/`卸载`…，"UninstallMyth.Cool" 这种没有分隔符的也得中）、
  **子串**（CJK：帮助/说明/官网/更新/许可…）、**整词**（ASCII：help/readme/manual/update/license/about…）——
  整词匹配是为了不误伤 "HelpDesk Pro"、"UpdateHub"
- 全十六进制名字（内部 id 漏进菜单）、目标不存在、目标不是可执行类（`.exe/.bat/.cmd/.msc/.cpl/…`）
- **实测**：`skipped(junk=26 web=4 missing=6)`，"卸载 PixPin / Uninstall 鸣潮 / Ryzen Master Help Guide /
  Python 3.12 Manuals" 都没进来

**与上一轮的联动**：自动发现加的东西可以在「快捷项管理」里按**来源筛选**（全部 / 手工·导入 / 自动发现）
一次性清理，**删掉的会被墓碑挡住，重扫也不会回来**。实测：删掉一条扫出来的
`AMD Bug Report Tool` → `MXRUN_SELFTEST_DISCOVER=force` 强制全量重扫 →
`seen=107 added=0 existing=100 tombstoned=1` ✓

**默认开 + 不打扰**：`cfg:discovery` 缺省即开；扫完只改状态行（"自动发现 94 个应用…可在设置里关闭"），
**不弹提示、不抢窗口**——扫描随时可能结束，抢正在打字的用户的窗口比不告诉他还糟。设置页有开关 + "现在扫一次" + 上次结果。

**测试**：`cargo test` **78 项**（新增 7 项：垃圾名三类匹配（含 HelpDesk 这种反例）、路径大小写/环境变量归一化、
只认可执行类、目录遍历、增量缓存的失效、去重集合来自真实条目的路径、条目来源稳定）。

**调试开关**：`MXRUN_SELFTEST_DISCOVER=force`（忽略缓存全量重扫）、
`MXRUN_SELFTEST_SOURCE=discovered|curated`（管理器先按来源筛选，便于脚本化删除）。

**没做的**：UWP（43 条，含"设置"这种可能真想要的；需要按 parsing name 取图标那条路）；失效项清理
（卸载后残留的条目，`health` 字段仍然没人算）；管理器的按来源**批量**删除（现在是一条条删）。

### 2.15 键盘流补全（2026-09-17 完成，实测）

**用户拍板的两处**：序号用**现代小序号**（不是原版 `*1|` 前缀）；`;`/`'` **照搬原版**（裸键执行第 2/3 项，
代价是这两个符号打不进搜索框）。

**先读了原版源码再动手**（GBK 转码后检索）。关于"条目自己带数字怎么办"，原版的处理是三件事：

1. **序号是固定两字符字段 + `|` 分隔**（`untShortCutMan.pas:1058-1081`）：第 1 位 = `*`（要参数）/ 空格，
   第 2 位 = 序号（`(i+1) mod 10`，第 10 项显示 `0`），紧跟 `|`；第 11 项起是 `  |`。
   显示形如 ` 1|chrome | Google Chrome`、`*2|b | 百度搜索`
2. **匹配用挂在行上的对象**（`AddObject(…, TObject(Item))`），不是显示字符串 → **序号永远搜不到**，
   打 `360` 只按关键字匹配
3. **按键只认 Ctrl/Alt+数字**（`frmALTRun.pas:1562-1586`，主键盘 48-57 + 小键盘 96-105），
   所以**打数字永远是搜索**；`;`(186) = 第 2 项、`'`(222) = 第 3 项是**裸键**（`:1588-1608`）

**MxRun 的落地（按用户选择）**：序号做成行首一个**淡灰小数字**（不挤关键字与命令行），
`*`（需参数）仍留在副标题。

**裸数字键（用户 2026-09-17 追加要求）**：一开始只做了 `Ctrl/Alt+数字`（照原版），用户问"呼出后不能直接按数字打开吗"，
于是改成**分状态**：

| 状态 | 数字键行为 |
|---|---|
| **输入框为空**（刚呼出、还没打字） | **裸数字 = 执行第 N 项**（`1`..`9`，`0` = 第 10 项）——"呼出 → 看列表 → 按 3" |
| **输入框有内容**（正在打字） | 数字**照常输入**——`python 3.12`、`3.12`、`win 11` 这类查询必须能打 |

这和原版"空输入框按空格 = 执行第 1 项"是同一个思路：**空框时按键是命令，打字时按键是输入**。
定这条之前先量过代价——**真实数据里没有任何以数字开头的条目**（开始菜单 0/175、手工清单 0/72），
所以"从空框开始打不出数字开头的词"这件事在用户这里不存在；万一将来有，用后面的字符也能搜到
（`7-Zip` 打 `zip`）。`;`/`'` 保持不变（两种状态下都能用，等于多留一组快捷键）。

**这一轮补上的**（都对齐原版）：

| 键 | 行为 | 原版依据 |
|---|---|---|
| **单击** | 只**选中** | 原版：单击选中 |
| **双击 / 中键** | 才执行 | 原版：双击/中键执行（之前 MxRun 单击即执行——条目上百后这是误触风险） |
| **裸数字（空输入框）** | 执行第 N 项 | 用户要求；原版只有 Ctrl/Alt+数字（见上） |
| `Ctrl/Alt+数字`、`;`、`'` | 直接执行第 N 项（**任何状态都能用**） | 见上 |
| `Tab` / `Shift+Tab` | 当 ↓ / ↑ | 原版 actUp/actDown 的 SecondaryShortCuts |
| **窗口拖动** | 按住卡片空白处挪 | `ReleaseCapture` + `WM_NCLBUTTONDOWN(HTCAPTION)`（`drag_window`） |
| **位置记忆** | 记住挪到哪，下次还在那 | 原版 `WinTop`/`WinLeft` → `cfg:win_x`/`win_y` |
| **托盘单击** | 切换显隐（原来是双击） | 原版 `OnClick = OnDblClick` |
| `Ctrl+C` | 复制选中项的命令行 | 原版窗体快捷键 |
| `Ctrl+L` | 最近列表（最近 7 天用过的，最近优先） | 原版"最近列表" |

`↑↓` 首尾循环**本来就有**（`(i+1) % len`），这次只是确认并写进文档。

**实现细节值得记的**：

- **拖动用的是"把窗口交给系统"**：`SendMessageW(WM_NCLBUTTONDOWN, HTCAPTION)` 会让 DefWindowProc 进入
  系统自己的移动循环，**这个调用会一直阻塞到用户松手**——所以它一返回就能 `GetWindowRect` 存档位置，
  不需要任何"拖动结束"事件（这正是 AltRun 的做法）
- **位置恢复要夹进屏幕**：`place_for()` 把记住的坐标 `clamp` 在 `(0,0)..(屏-窗)` 内。
  实测存 `9999,9999` → 恢复成 `2760,1040`（3440×1440 屏的右下角）——换显示器/拔掉副屏也不会把卡片弄丢
- **顺手修掉一个真 bug**：`apply_window_size`（切管理器/卡片时改尺寸）原本每次都重新居中，
  会把用户拖好的位置**弹回中间**；现在也走 `place_for()`
- **托盘单击要防抖**：单击切换 + 双击不能再切一次（双击会连发两次 Click），350ms 内的第二次点击吞掉

**实测（无键盘）**：

```
位置记忆：save 120,80 → 下次启动 window: placed at 120,80 (remembered) → 再启动仍 120,80
夹取：    save 9999,9999 → placed at 2760,1040
最近列表：没启动过任何东西 → recent_only=true rows=0
         真的启动一次后     → recent_only=true rows=1
数字键：  MXRUN_SELFTEST_ROW=2（等于空输入框按 2）→ selftest: row 2 -> "BBB Tool" (3 rows)
         → execute: BBB Tool → 只产生了 mxrun-f2.txt（f1/f3 没动）
无回退：  冷启动 253ms、后台自动发现 301ms、索引 100 条 0ms（与上一轮持平）
```

**测试**：`cargo test` **82 项**（新增 4 项：裸数字必须是搜索文本（`digit_row`）、
**裸数字只在空框时执行**（`bare_digit_row`）、`;`/`'` 的行号、
最近列表时间窗边界——顺带测出"时钟回跳时未来时间戳算最近"这条**故意**的宽容行为）。

**调试开关**：`MXRUN_SELFTEST_WINPOS=x,y`（模拟拖到某处并记住）、`MXRUN_SELFTEST_RECENT=1`（启动即切最近列表）、
`MXRUN_SELFTEST_ROW=N`（等于空输入框按 N，**会真的执行**，只对临时档案用）。

**原版真正的"打字时按数字"机制（2026-09-19 补查，之前漏了）**：不在按键处理里，而在**输入变化处理**里
（`frmALTRun.pas:1411-1470`）——**"尾部字符如果让搜索变成 0 结果，就当成命令来解释"**：

```pascal
if lstShortCut.Count = 0 then              // 加了这个字符后，列表空了
begin
  if EnableNumberKey and m_LastKeyIsNumKey
     and (edtShortCut.Text[Length(edtShortCut.Text)] in ['0'..'9']) then
    → Execute(m_LastShortCutPointerList[k - 1], ...)     // 上一次列表的第 k 项
  if 最后一位是空格 then
    → Execute(m_LastShortCutPointerList[m_LastShortCutCmdIndex], ...)  // 上一次高亮的那项
end;
```

`m_LastShortCutPointerList` 由 `GetLastCmdList`（`:2350`、每次列表刷新后调用 `:1491`）留快照。
所以原版哲学是"**空结果 + 尾字符 = 命令**"：数字 = 第 N 项、空格 = 当前项（我们天天用的"空格执行"就是同一条分支）。

**为什么不照搬**：它成立的前提是"加数字后结果恰好为 0"——原版是正则子串匹配，我们是 nucleo 模糊 + 拼音 + 标题/命令行全字段，
`b3` 这种常能糊到东西 → 机制会变成"有时灵有时不灵"；而且它在**空列表**上直接启动程序、无确认无提示。

**2026-09-19 在真实库副本（157 条）上实测触发率**：

| 查询 | 可见行数（闸门后） | 原版规则 |
|---|---|---|
| `b` → `b3` | 8 → **2** | ❌ 不触发（数字真的在筛选） |
| `chrome` → `chrome2` | 1 → **0** | ✅ 触发（但上次只有 1 行 → `k=2>1` → 什么也不做） |
| `steam` → `steam3` | → **0** | ✅ 触发 |
| `pycharm` → `pycharm6` | 1 → **1** | ❌ 不触发（`pycharm64` 靠模糊匹配活着） |
| `godot` → `godot4` | 2 → **2** | ❌ 不触发（同上；即便触发也会被守卫②挡住：2 行没有第 4 项） |
| `system` → `system3` | → **0** | ✅ 触发 |
| **`zz`**（纯垃圾查询） | **8** | ⚠️ **连乱码都有 8 行** —— "死查询"在我们的管线里近乎绝迹 |

**结论**：原版规则的触发条件从"查询的性质"变成了"数据的性质"——同一个手势（打完关键字按数字）会出现三种结果，
用户无法预测。**能救回一部分的是分数闸门**（弱匹配被整批丢掉，所以"可见列表为空"比"匹配数为 0"常见），
没有闸门这条机制会更死。另外反向的代价也要记住：**若把数字做成"永远当命令"（不依赖这个前提），
才会真的伤到搜索**——实测你的数据里 19/177 个开始菜单标题、4/73 个手工关键字**含**数字
（`pycharm64`、`System32`、`Python 3.12`、`Godot_v4.7`…），数字打不进去就等于这些条目按名字搜不到。

**替代方案（待拍板）**：显式前缀 `#3`（在**当前**结果里选第 3 项），可预期、有视觉提示，并且和 `@` 文件搜索共用同一套前缀注册表；
或"情形 3 扩展"——把触发条件从"数字杀死了查询"放宽成"**数字对结果没有任何筛选作用**"（前后结果集相同），
这是模糊匹配下最接近原版手感、又能可靠触发的做法。

### 2.16 打字时的数字（原版规则 + 模糊适配，2026-09-19 完成并实测）

用户拍板：**情形 3 要做、触发就立即执行（同原版）、显式前缀用 `#`**。落地规则（`digit_verdict`，纯函数 + 单测）：

```
尾部是数字 d（0 = 第 10 项）且输入非空，并且：
① 去掉 d 的前缀 · 就是上一次的输入（这个数字是刚追加的那一个字符）
② 前缀里一个数字都没有          ← 保险，挡住"正在打含数字的名字"（pycharm64 / x64 / Python 3.12）
③ 当前可见列表为空（数字杀死搜索，原版情形）或与前缀的列表完全相同（数字没起作用，情形 3）
④ 前缀那份列表至少有 d 项        ← 原版守卫②
→ 执行前缀列表第 d 项 + 清空输入框；否则数字就是普通搜索字符
```

**显式前缀 `#`**：`b#3` = "b 的结果里第 3 项"，`#3` = 全列表第 3 项，`#0` = 第 10 项。任何状态都能用，
不依赖"搜索是否死掉"。`refresh_search` 用 `#` **之前**的文本当查询，所以打 `b#` 时列表仍是 b 的结果（边打边看）；
只输入 `#` 时状态行提示可选范围。`#` 与数字都照常输入（不是按键劫持），代价是 `#` 不能作为搜索词的首字符。

**为什么加保险②**：推演时发现原版规则在模糊匹配下有个洞——**用户正在打的数字本身常常"不改变结果集"**
（`pycharm` → `pycharm6` 仍匹配 `pycharm64`），会误判成"选第 6 项"，而 19/177 个标题含数字，打字经过数字是高频动作。

**实测（两套）**：

| 场景 | 结果 |
|---|---|
| 合成清单 `al2`（`al` 2 行 → 数字杀死搜索） | ✅ `run row 2 of "al" [Alto Tool]` → 真的写出了该条目的文件 |
| 合成清单 `al9`（前缀只有 2 行） | ✅ 保持输入（`no-such-row`，守卫②） |
| 合成清单 `lab1`（`lab` 2 行 → `lab1` 仍是同一批） | ✅ 触发（**情形 3**）→ 执行 `Lab One` |
| 合成清单 `q55` | ✅ 保持输入（`prefix-has-digit`，保险②） |
| 合成清单 `al#2` | ✅ 执行第 2 项（显式前缀） |
| **真实 157 条列表**：22 组"单字母 + 数字"（干跑，不启动） | **触发 6 / 22（27%）**，其余全是 `digit-filters`（数字真的在筛选，例如 `s`→`s3` 8 行变 1 行） |

**结论（要记住的期望值）**：原版靠"关键字子串匹配"做到 ~100% 触发，我们在模糊匹配下**约 1/4**。
可靠的路径始终是 `#N` / `Ctrl·Alt+数字` / `;` / `'`；隐式规则是"顺手就能用"的额外便利，不是主路径。
每次判定都写日志（`digit: "b3" -> keep input (digit-filters; prev="b" 8 rows, now 2 rows)`），用几天后可以回头看准不准。

**新调试开关**：`MXRUN_SELFTEST_TYPE='al2|lab1|b#3'`（逐字符模拟打字，用 `|` 串多个用例，会真的执行）、
`MXRUN_SELFTEST_DRYRUN=1`（只判定不启动，用来量触发率）。

**已知代价**：① 空框裸数字 + 这个规则一起吃掉了"以数字开头的输入"，所以**计算器没法从数字开始打**
（`1+2` 的第一个 `1` 会被当成"第 1 项"）；要修的话给计算器一个显式前缀（如 `=1+2`）最干净。② `#` 不能作查询首字符。

### 2.17 缺口修复（2026-09-19 晚）

**① `Alt+F4` 只隐藏、不退出**（对齐原版）：`App::ui` 开头检查 `ctx.input(|i| i.viewport().close_requested())`，
发 `ViewportCommand::CancelClose` + `hide_window`；托盘"退出"先置 `QUITTING` 再 `close_window()`，那一次才真退。
**实测**：窗口可见时 `PostMessage(WM_CLOSE)`（等同 Alt+F4）→ **进程存活、窗口仍存在但已隐藏**，日志 `hide: close requested (Alt+F4) -> hiding, not exiting` ✓

**② Esc 之后输入框失焦、打字没反应**（用户 2026-09-19 报的真实 bug）：根因是 **egui 的焦点导航在每帧开始前读原始事件**
（`Memory::begin_pass`：`Escape` → `focused_widget = None`、`Tab` → 移动焦点），而 `TextEdit` 的默认 `EventFilter`
只捕获方向键、**不捕获 Tab 与 Escape** → Esc 把焦点交了出去，窗口又没变（没有 hidden→visible 过渡，所以不会自动重新聚焦）
→ 之后敲键盘哪儿也不去。三层修复：
1. 搜索框声明 `EventFilter { tab: true, escape: true, .. }`，让 egui 不抢这两个键（Tab/Shift+Tab 归我们的列表导航）
2. Esc 清空输入后 `want_focus = true`（和参数框的 Esc 分支一致）
3. **兜底**：启动器视图里若"没有任何控件持有焦点、也没有弹出菜单"，就把这一帧输入的文字直接追加进搜索框并重新聚焦
   （覆盖点行选中、右键菜单关闭等一切失焦来源），日志 `focus: recovered typed text "..."`

**③ 行数上限不动**（用户决定）：`MAX_ROWS = 8` 保持不变（"太多的上限没有意义"），因此 `Ctrl/Alt+9`、`0` 仍够不到。
**但 `@` 文件搜索的结果上限必须独立计算**（`@` 是另一条管线，不该受启动器 8 行限制）——写进 `命令模型设计.md` §9。

**④ 数字键提示行**：用户决定暂不做。

**已知边界（记录，不修）**：窗口**隐藏时**收到的关闭请求不会被我们的 `CancelClose` 拦到（隐藏时 eframe 不跑 `ui()`），
实测那种情况下窗口被销毁、进程残留。正常场景（可见时 Alt+F4）没问题；真要兜住得拦 Win32 的 `WM_CLOSE`（子类化窗口过程），目前不值得。

### 2.18 计算器改成显式前缀 `=`（2026-09-19 晚，用户要求）

**问题**：内置计算器原本是**隐式**的——查询"全由数字与运算符组成且含运算符"就求值。而空框裸数字规则会把 `1+2` 的**首位数字**当成"执行第 1 项"，
于是**从空框根本打不出以数字开头的算式**（这是裸数字功能带出来的回归）。

**改法**：前缀 `=`（用户拍板）——`=1+2` 显示 `= 3`。
- `refresh_search` 里 `is_calc_mode()` 命中时**完全不搜索**（列表为空、数字规则/选行器都不参与），只求值
- 表达式为空或求值失败 → 列表位置显示"输入算式，例如 =1+2"，状态行说明支持 `+ - * / % ^` 与括号
- **回车不做任何事**（绝不再弹"无匹配 → 添加它"，那也是错的）；Esc 两级语义不变
- 隐式那条路**删掉**了（一个功能一条路，避免"有时能算有时不能"）

**顺带修掉三个真问题**（写测试时才发现）：
1. **`100/8` 原来是 `12`** —— `evalexpr` 两边都是整数时做**整数除法**。含 `/` 的表达式先把数值字面量变成浮点（`100/8` → `100.0/8.0` → **12.5**），
   其余保持整数精确运算（所以 `2^10` 正好是 `1024`，不会变成 `1024.0000000000002`）
2. **`1/0` 会显示 `inf`** —— 浮点化之后除零得到 `inf`，现在把非有限值判为"无解"（显示输入提示）
3. **浮点噪声**：`0.1+0.2` 显示 `0.30000000000000004` → 现在格式化成 `0.3`（十位小数裁尾零），同时保证极小值不被抹成 0（`1e-15` 仍显示 `0.000000000000001`）

**前缀家族成型**（都是"字符 = 模式"，不是按键劫持）：`=` 计算器 · `#` 选行 · 将来 `@` 文件搜索。

**实测**（`MXRUN_SELFTEST_TYPE` 逐字模拟）：`=100/8` → **12.5**、`=0.1+0.2` → **0.3**、`=2^10` → **1024**、
`=1/0` → 无解提示、`=1e-15` → **0.000000000000001**；测试 85 → **86 项**。

### 2.19 卡片改回不透明（2026-09-19 晚，用户报告"半透明很影响看"）

**根因**：卡片填充的默认 alpha 是 **235**（`card_alpha`，当初 E2 spike 留的旋钮）——`MXRUN_BACKDROP` 默认是空串，
`apply_backdrop` 直接 return，所以**没有任何系统材质**，桌面是直接从卡片底下透出来的。**改成默认 255（完全不透明）**，
`MXRUN_CARD_ALPHA=235` 仍可回到旧观感（留给将来做视觉时的旋钮）。

**注意仍然保留的东西**：`with_transparent(true)` + `clear_color = TRANSPARENT` **不能去掉**——圆角是靠"面板不填满四个角、
露出透明像素"实现的；现在是"卡片本身不透明、四个角透明"，阅读性和圆角都在。

**教训**：E2 spike 期间为了试验材质，把"半透明"当成了默认值留在主干上，而**用户的第一诉求是"看得清"**。
以后凡是"试验性外观参数"，默认值必须选**最保守的那个**（这里就是全不透明）。

### 2.20 底部状态栏与候选项重叠（2026-09-19 晚，用户截图报告）

**现象**：最后一行候选项被底部状态栏（`Alt+F1 呼出 / 隐藏 · Enter/空格 执行 …`）压住，两行字叠在一起。

**根因**：状态栏是**在列表之后**用 `Layout::bottom_up` 画的，而列表是 `ScrollArea::auto_shrink([false, false])`——
滚动区已经把整张卡片的高度吃光了，后画的 `bottom_up` 布局**一点空间都申请不到**，只能在原位置画，于是压在最后一行上。

**修法**：状态栏改成 `egui::Panel::bottom("mxrun-status")`（egui 0.36 把 `TopBottomPanel` 统一成了 `Panel`，
`show_inside` 也改名 `show`），并且**放在列表之前**——面板会先从可用矩形里切走底部那条，列表再拿剩下的。
同类问题一并处理：**"无匹配结果"/"没有匹配的条目"这类空状态文字也移到滚动区之前**（否则同样会被挤出卡片）。
管理视图一个毛病，一起改了。

**加了防回归的几何自检**（`check_status_overlap`）：列表底边比状态栏顶边低 1px 以上就写日志
`layout: list (..) overlaps the status bar (..)`；带 `MXRUN_SELFTEST_RECTS=1` 时把两个矩形都记下来。**实测**：

```
启动器（8 行）：list 68..361, status 361..381 (no overlap)
管理视图（157 条）：list 80..521, status 521..541 (no overlap)
```

（顺带发现：自检的第一版把"共边"误报成重叠——`Rect::intersects` 对**相接**的矩形也返回 true，改成"侵入 > 1px"才是真重叠。）
代价是列表少用 20px 高度（以前它是钻到状态栏底下的），这正是它该有的样子。

### 2.21 没地方拖动窗口（2026-09-19 晚，用户报告"好像没有地方供拖动"）

**根因是我自己**：拖拽手柄一直注册在 `ui.max_rect()`（**内容区**）上，而这一轮的三处改动把内容区的空白吃干净了——
卡片改不透明、列表 `auto_shrink(false)` 铺满整张卡、状态栏变成面板占了底部。于是"手柄"只剩下几个 6px 的间隙，
用户当然找不到地方拖。

**三层修复**：
1. **手柄矩形改成整个窗口**（`ctx.content_rect()`）：实测 `[[0,0]-[680,400]]`，与窗口等大——连 18px 外边框一起算
   （顺带确认交互裁剪区也是整窗，边框不在裁剪之外）
2. **列表行也变成可拖拽**（`Sense::click_and_drag()` + `drag_started()` → `drag_window`）：列表是卡片上最大的一块，
   原版 AltRun 也是"按住列表背景就能拖"。egui 有自己的拖动阈值（约 6px），所以**单击选中、双击执行完全不受影响**
   （管理视图的行同样处理）
3. **加一个看得见的抓手**：卡片顶部中间一条 34×3 的暗色小圆条（现代无边框窗口的通用暗示），
   它那一整条横带都是可拖区域。代价：列表高度少 10px

**为什么拖拽只能人眼验证**：`drag_window` 里 `SendMessageW(WM_NCLBUTTONDOWN, HTCAPTION)` 会进入系统自己的移动循环、
**阻塞到真实鼠标松开**——用合成事件模拟拖动会让进程永远卡住（所以不做这种测试）。
能自动验的只有几何：手柄矩形、列表/状态栏不重叠，都已记进日志（`MXRUN_SELFTEST_RECTS=1`）。

### 2.22 卡片标题条 + 拖动的真 bug（2026-09-19 晚，"你不能自己验证吗？"）

**用户要求**：① 卡片上加一个软件标题；② 反问我为什么不能自己验证拖动。**两件都做了，而且验证挖出一个真 bug。**

**标题条**：卡片顶部左边 `MxRun`（12pt 灰）、右边一条 26×3 的抓手圆条，整条都是拖拽区。
窗口标题（任务栏 / Alt+Tab 上显示的）本来就是 `MxRun`（eframe 默认取 crate 名），顺手显式写成 `.with_title("MxRun")`，免得改名时静默跟着变。

**拖动其实"隔一次失败"**——用**真实鼠标输入**验证才发现的：

```
修复前： ✅ 拖标题条 60,30    ❌ 拖标题条 0,0    ✅ 拖列表行 45,23
```

根因：`drag_window` 里 `SendMessageW(WM_NCLBUTTONDOWN, HTCAPTION)` 进入的**模态移动循环自己抽消息**，
把鼠标**松开**事件吃掉了 → winit/egui 从没收到"松开" → egui 一直以为指针按着 →
**下一次按下不算新按下，拖动被忽略**。修法：移动循环返回后**自己补一条 `PostMessageW(WM_LBUTTONUP)`**，让输入状态追上。
这也解释了用户"好像没有地方供拖动"的体感：拖一次成功、再拖一次没反应。

**状态栏那条原本也不行的原因**：egui 的 `Panel` 会在自己的边缘注册 `click_and_drag`（用来拖拽调整大小），
把按下事件吃掉了；在面板之上再盖一层 `Sense::drag()` 的 interact（后注册的在上）即可。

**关键方法（值得复用）**：egui 合成事件测不了这个——必须用 `mouse_event` + `SetCursorPos` 发**真实**输入，
系统的移动循环才会正常收到松开。**验证脚本已进仓库：`tools/verify-drag.ps1`**
（连续拖三处 → 核对窗口位移 + 日志里的 `position saved` → 退出码 0/1）。
⚠️ 这个 .ps1 **必须带 UTF-8 BOM**：PowerShell 5.1 读无 BOM 的 UTF-8 脚本会按 GBK 解析，中文注释直接把它读成语法错误（老坑重演一次）。

**全卡片拖拽扫描（自动化，实测）**：

| 位置 | 能拖 |
|---|---|
| 标题条 / 列表任意一行 / 状态栏 / 卡片底边 / 左右外边框 | ✅ |
| 搜索框那一行 | ❌ **故意**（那里要能选文字） |

**测试**：86 项不变（拖拽属人机交互，靠上面这个脚本 + 人工确认）。

### 2.23 悬停抢选中，键盘 ↑↓ 失效（2026-09-19 晚，用户报告"候选项会跟着鼠标走"）

**现象**：鼠标只要停在候选区，↑↓ 每按一次就被鼠标抢回原选中项——键盘看着就是坏的。

**原版怎么做的（用户问的，查了源码）**：`frmALTRun.pas` **没有任何 `OnMouseMove`** —— 悬停**什么都不做**（不高亮、不改选中）。
选中只由三件事改变：
1. 键盘 ↑↓ / PgUp / PgDn（`FormKeyDown` 里 `lstShortCut.ItemIndex := ...`）
2. **左键点击**（TListBox 自带行为）
3. **右键**：先 `lstShortCut.Perform(WM_LBUTTONDOWN, MK_LBUTTON, (y shl 16) + x)` **模拟一次左键把该行选中**，再 `actSelectChangeExecute` + 弹菜单（`:2531-2535`）
4. 中键：`actExecuteExecute` → 执行**当前选中项**（`:1356-1363`，它**不**先改选中）

**修法**：删掉"悬停即选中"（启动器与管理器两处都删）——选中只由键盘和点击改变。
保留一个**很淡的悬停底色**（alpha 7，选中是 18）作为"可点击"的反馈：它用**上一帧**的 hover 状态画
（背景必须先于 `Response` 画出，一帧延迟在这么淡的色调上看不出来），而且**绝不改 `selected`**。

**验证（真实键鼠，可复现）**：`tools/verify-hover-vs-keys.ps1` —— 点第 1 行（鼠标就停在那行不动）→ 按 ↓↓ → 回车，
期望执行第 3 行。**并且验证过这个测试抓得住 bug**：把"悬停即选中"临时加回去重跑 → 失败，执行的是**第 1 行**
（正是用户描述的现象）；恢复修复后 → 通过。这一步很重要：一个永远通过的测试等于没有测试。

**顺带确认的差异（有意保留）**：我们的中键执行**鼠标所在行**，原版执行**当前选中行**——鼠标点在哪儿就开哪儿更符合直觉，
且左键点过之后两者本来就一致。

### 2.26 视觉第二批：呼出动画 + DWM 圆角 + 模式徽标（2026-09-19 完成并实测）

**① 呼出动画（淡入 + 上浮）**
- 淡入：`Ui::set_opacity` 一次性盖住卡片内容，卡片填充与 1px 描边同步按 `anim_t` 缩放
  （描边不跟着淡的话，动画开头会先出现一圈"空框"）
- 上浮：4px，窗口位置在动画期间逐帧 `SetWindowPos`，落地时正好是 `place_for()` 算出的位置
- 时长 **100ms**（`ANIM_MS_DEFAULT`），缓出曲线 `1-(1-t)³`；**`MXRUN_ANIM_MS=0` 可关**（想回到 AltRun 那种"啪一下"就用它）
- 只请求自己需要的帧（动画期间 `ctx.request_repaint()`，结束即停）——**"空闲不跑 `ui()`"这条没破**，冷启动首帧仍 231ms
- **冷启动也要淡入**：第一版只在"隐藏→显示"过渡里启动动画，结果冷启动不淡（`prev_visible` 初值就是 true），实测发现的
- 隐藏**不做**淡出：隐藏是托盘/热键线程直接 `ShowWindow(SW_HIDE)`，为 80ms 淡出引入线程间状态不划算，而且瞬隐更跟手

**实测**（把动画拉长到 1500ms 才抓得住）：动画中途卡片底色 `(2,3,3)` ≈ 几乎全黑 → 静止后 `(26,27,34)` 满值 ✓；
上浮用几何日志证明（`MXRUN_SELFTEST_RECTS=1`）：`y 503 → 501 → 500 → 499`，`dy` 从 3.5 平滑收到 0 ✓

**② DWM 原生圆角**：`DwmSetWindowAttribute(hwnd, DWMWA_WINDOW_CORNER_PREFERENCE=33, DWMWCP_ROUND=2)` → 返回 `Ok(())`（Win11 22H2+ 有）。
这是**为第三批材质铺路**（材质会铺满窗口矩形，那时"靠透明角做圆角"会失效）；`MXRUN_ROUND=0` 可关。
圆角放大图确认边缘干净；**DWM 的投影我验证不了**（在窗口矩形之外，`PrintWindow` 抓不到），要人工看。

**③ 模式徽标**：标题条右端一个小胶囊，显示当前模式——`计算器`（绿）/ `最近列表` / `按按序号选行`（橙）。
作用是"列表突然空了/变了"时不再像 bug（计算器模式列表本来就是空的）。
⚠️ 踩坑：徽标最初写成裸的 `ui.with_layout(right_to_left, ...)`，**它吃掉了整张卡片的剩余区域**，把搜索框挤到了卡片底部
（截图一看就知道了）——**必须套在 `ui.horizontal(...)` 里**才是一行。

**测试**：86 项不变；交互回归（拖拽、悬停 vs 键盘）全过。

**②b 圆角返工：两套圆角打架（用户截图："背景色被吸到圆角边缘"）**
用户截图里卡片四角有一圈"壁纸渗进来"的痕迹。根因：**同时存在两套圆角**——
我们自己的卡片圆角是 **14px**（靠"角上透明"实现），DWM 原生圆角是 **8px 的裁剪**；
两条弧线不重合，中间那圈月牙就露出桌面 ✗。

修法：**让两套取同一个半径** —— `CARD_RADIUS = 8`（与 Win11 `DWMWCP_ROUND` 一致），**并且照样画自己的圆角**：
- DWM 生效时：两条弧线重合，没有月牙缝 ✓
- DWM 万一对透明窗口不裁剪（这是已知的不确定点）：我们自己的 8px 圆角兜底，**不会变成方角** ✓
- 没有采用"矩形交给 DWM 裁"的方案，因为它把"方角"的风险全押在 DWM 上

代价：卡片圆角从 14px 变成 **8px**（比原来稍微"紧"一点）。
想回到 14px 圆润观感就把 DWM 关掉：`MXRUN_ROUND=0`（此时只有我们自己的圆角，但也不会有 DWM 的系统投影）。
**实测**：卡片色从对角线第 4 像素开始 ✓（8px 弧线正常）、放大 8 倍看边缘干净 ✓。
**仍需人眼**：四角还有没有渗色、以及小卡片有没有系统投影。

**②c 用户验收通过（2026-09-19）**："已经好了，不渗颜色了，而且有投影了，很好" ——
即：**8px 对齐方案正确**，且 **DWM 圆角确实对透明窗口生效并带来了系统投影**（这条之前是"不确定点"，现在有结论了：
Win11 25H2 上 `DWMWCP_ROUND` 对 `with_transparent(true)` 的无边框置顶窗口有效）。
**推论**：以后要做材质（Acrylic），DWM 这条通路是可靠的，不必再怀疑它会不会被透明窗口忽略。

### 2.27 视觉第三批（改版）：明暗主题联动 + 手动切换（2026-09-19，用户点单）

用户要求："先做明暗主题吧，并且给一个设置可以主动切换"。**材质（Acrylic）不做**，理由是有数据支撑的：
卡片不透明时材质根本看不见，要看见就得让卡片半透明——而那正是用户明确否掉的"很影响看"；浅色主题才是真需求。

**改法**：
1. **调色板从"一堆常量"变成"两张表 + 运行时选择"**：`struct Palette` + `DARK`/`LIGHT` 两个实例，
   `pal()` 一次原子读返回当前表（主题一整个会话才换一次，不值得把 `&Palette` 穿过每个绘制闭包）。
   58 处颜色用法一次性迁到 `pal().xxx`（脚本替换 + 词边界正则，先长后短，避免 `TEXT` 吃掉 `TEXT_DIM`）。
2. **egui 自身的控件也要跟着换**：`ctx.set_visuals(Visuals::light()/dark())`——文本框、按钮、复选框、滚动条都是 egui 画的，
   调色板管不到；顺手把 `extreme_bg_color` 设成透明，否则搜索框会被 egui 自己的深色底盖住卡片。
3. **浅色不是把深色反过来**：几个必须重算的颜色 —— 强调色从亮琥珀 `(255,190,80)` 改成深琥珀 `(176,106,0)`（白底上亮琥珀读不清）、
   成功色、危险色同理压暗；卡片用略冷的白 `(250,250,252)` 而不是纯白（台灯下不刺眼）。
4. **设置项**：`cfg:theme = system|dark|light`（默认 `system`），设置页新增「外观」段三个可点选项 + 一行说明；
   点击立即生效（`set_config` + `apply_theme_choice` + `apply_card_style` + `request_repaint`）。
5. **跟随系统的实现**：读 `HKCU\...\Themes\Personalize\AppsUseLightTheme`，
   **每次呼出时重读**（几乎零成本，且不引入空闲轮询——"空闲不跑 `ui()`"没破）。
   设置页那行说明**报告系统真实值**（`SYSTEM_LIGHT`），而不是当前生效值——第一版说反了（我用 `MXRUN_THEME` 强制浅色时它显示"系统为浅色"），已修。
6. **调试开关** `MXRUN_THEME=system|dark|light`（覆盖设置，专供截图与 A/B）。

**实测**：深色 `theme-dark.png` / 浅色 `theme-light.png` 两张截图对比；
**对比度量像素**：深色标题-底 ≈ **5.3:1**、浅色 ≈ **8.8:1**（都过了 WCAG AA 的 4.5:1）；设置页在两种主题下都渲染正常，
"跟随系统（系统当前为深色）"与实际系统一致 ✓。测试 86 项不变。

### 3.1 右键集成的三条设计约束（**已实现，留档**）

从 §2.8 的 AltRun 实测行为反推——实现时别丢：

1. **"不打扰"是这个交互的灵魂**：只弹一个加项小确认框，**主窗口全程不显示**（原版"已运行"和"未运行"两种情况都不显示）。顺手把主窗口拉出来，手感就变了。

3. **两个坑别照抄**：① 关键字或命令行**任一为空**时，原版静默降级成"空行分隔项"——MxRun 直接拒绝并留在输入态；② 原版加项路径**绕过单实例保护**（互斥体检查在加项分支之后，两个实例可能同时写列表文件）——MxRun 走交接把路径交给主实例处理，只有一个写者。

## 7. 踩坑记录（本次新增，避免重复踩）

1. **egui 空闲时不调用 `ui()`** —— 任何轮询式检查（如失焦检测）都必须配 `ctx.request_repaint_after(...)`，否则是死代码。
2. **`MainWindowHandle` 不是可见性探针** —— 它是句柄。判断窗口是否可见要用 Win32 `IsWindowVisible`。
3. **`SendKeys` 只送到前台窗口** —— 从自动化环境启动的 MxRun 拿不到键盘焦点，按键会落到别的窗口（有误伤风险）；`WM_CHAR` 投递也进不了 egui。**自动化测试不能验证键盘交互，必须人工确认**。
4. **运行中的实例会锁住 `target/release/mxrun.exe`** —— 重新构建前先关掉实例，否则 cargo 报 `拒绝访问 (os error 5)`。**构建后务必看一眼 exe 时间戳**。
   **而且它还会干扰测试**：残留实例会抢前台窗口，让"真实窗口隐藏/恢复"那条端到端测试失败。跑测试前先 `Get-Process *mxrun* | Stop-Process -Force`。
5. **控制台编码 / 读日志**：PowerShell 输出中文会乱码；读 UTF-8 日志必须用 `[System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)`，否则满屏乱码（**文件本身没坏**）。
6. **不要用 `Add-Type -MemberDefinition` + `\"` 转义** —— PowerShell 的转义符是反引号，用 here-string `@"..."@` 更稳。
7. **COM 是按线程的** —— 图标 worker 线程必须自己 `CoInitializeEx`，不能复用主线程的进程级 `Once`。
8. **`OnceLock` 懒初始化会骗人** —— `us_since_start()` 原来在第一次调用时才锚定起点，于是第一个调用者永远读到 0（我据此误判过"图标瞬间就绪"）。时钟要在 `main` 里锚定。
9. **PowerShell 里 `$env:VAR = ""` 等于删除变量** —— 想给程序传"空字符串"（自检开关的空查询）做不到，得换哨兵值或干脆不设。
10. **视觉工具会限流** —— `vision_describe` 返回 `VISION_RATE_LIMITED` 时改问法重试**没用**；本机也没装 tesseract（`spawn tesseract ENOENT`）。UI 截图验证要靠人工看一眼，或等下一轮再读。
11. **"看起来像遥测数据"的字段先查来源再信** —— AltRun 的 `F<n>` 我当成"使用次数"分析了一整轮，其实是作者模板里的预置权重（§2.7 与 `命令模型设计.md` §6.1.1）。**数据的出处比数据本身更重要。**
12. **GDI 截图拍不到这个窗口（2026-09-15，新踩）→ 2026-09-19 部分推翻，见下** —— 当时 `CopyFromScreen` / `PrintWindow` / 带 `CAPTUREBLT` 的 `BitBlt` 三路都只拿到**窗口背后的壁纸**（像素统计：卡片色占比 0%、无亮字像素），推断是 DWM 把 GPU 合成的窗口提到了**硬件叠加平面（MPO）**上。
    **2026-09-19 复测：`PrintWindow` 其实能截到完整画面**（`flag=0` 与 `PW_RENDERFULLCONTENT=2` 都行；卡片色像素占比 68% / 83%）。差别最可能是**当时卡片还是半透明的（alpha 235）**：`with_transparent(true)` 的窗口抓下来 alpha 通道可能全 0，像素统计就判成"什么都没抓到"；现在卡片不透明，同一路 API 正常。
    现成工具：`tools/screenshot.ps1`（`PrintWindow` + `PW_RENDERFULLCONTENT`，`-KeepOpen` 可自己起临时实例）。
    **结论修正：UI 视觉可以自己核对**，不用每次都让人肉截图；**推论**：以前判过"某个 API 不可用"的结论，条件变了要回头复验。
    顺带保留有效的那半条：自动化启动的进程**拿不到前台**，窗口会在 ~300ms 后 `hide: lost focus` 自己收起来 —— 所以要 `MXRUN_KEEP_OPEN=1` 关掉失焦隐藏再截/再测。
13. **harness 的 shell 是 Windows PowerShell 5.1，`Set-Content`/`Get-Content` 默认按 ANSI 处理** —— 2026-09-15 用 `(Get-Content -Raw) -replace … | Set-Content` 批量改 `main.rs`，把文件里的 UTF-8 中文与破折号**整片改成 `?`**（文件当场不是合法 UTF-8，cargo 报 "stream did not contain valid UTF-8"）。**改源码只用编辑器/`edit` 工具，永远不要用 PowerShell 文本管道重写带中文的文件**；读日志要显式 `[Text.Encoding]::UTF8`（见踩坑 5）。恢复办法：`git checkout -- <文件>` 后重做改动（当时改的都是本回合的编辑，代价可控）。
14. **PowerShell 里注册表路径含 `*` 会被当通配符炸开（2026-09-15，新踩）** —— `Test-Path "HKCU:\Software\Classes\*\shell\MxRun"` / `Get-ItemProperty` 同类写法会把 `*` 展开成 `HKCU\Software\Classes` 下的**所有类**，命令直接卡死（实测 120s 超时）。查这种路径要么 `-LiteralPath`，要么用 `reg query "HKCU\Software\Classes\*\shell\MxRun" /s`（`reg.exe` 不做通配）。
15. **`message_box` 会挡住脚本** —— `--import` / `--install-integration` 这类无窗口模式最后都会弹一个 Win32 汇总框，从脚本里 `Start-Process … -Wait` 会一直等下去。检查产物要在弹框**之后**、杀进程之前（`Get-Process *mxrun* | Stop-Process -Force` 会顺带关掉框）。
16. **剪贴板测试会被桌面上别的东西抢**（2026-09-16，新踩）—— `clipboard_round_trip` 写过探针后立刻读回，在有剪贴板管理器/输入法助手（用户正坐在电脑前用着）时会读到 `None` 而**失败**。修法：**先把用户的剪贴板还原，再断言**（失败绝不能把探针留在人家剪贴板里），探针读不回来时**跳过而不是失败**——那是环境在说话。同一类问题：任何"独占全局资源"的测试都要这样写。
17. **提交前钩子真的会拦自己人** —— 我在测试里写了个假用户目录路径（就是"`C:` + `\Users\` + 一个字母"那种形状），被 `pre-commit` 当成真实路径拒了两次（第二次是**文档里引用它**）。**这是钩子在正常工作**：假路径也别用那个形状，改用别的盘符 + 中性目录名（如 `R:\roaming`）；连"引用一下"都不行，写坑记录时用文字描述形状。
18. **egui 的焦点导航在"帧开始之前"读原始事件，`TextEdit` 默认不捕获 Tab/Escape**（2026-09-19，用户报的 bug 挖出来的）—— `Memory::begin_pass` 会先把 `Escape` 解释成"交出焦点"、`Tab` 解释成"移动焦点"，**这发生在我们的按键处理之前**，而 `TextEdit` 的默认 `EventFilter` 只捕获方向键。后果：**Esc 清空输入后输入框失焦，之后敲键盘完全没反应**（窗口没变，所以"隐藏→可见自动聚焦"那条路也不会触发）。修法三件套：给输入框声明 `EventFilter { tab: true, escape: true, .. }`；自己处理完 Esc 后 `want_focus = true`；再加一道"没有控件持有焦点时，把这一帧输入的文字塞进搜索框并重新聚焦"的兜底。**教训：任何"输入框突然不响应"的现象，先查焦点而不是查按键。**
19. **窗口隐藏时 eframe 不再跑 `ui()`**（2026-09-19 实测）—— 所以"靠 `close_requested()` + `CancelClose` 拦关闭"只对**可见**的窗口有效；隐藏状态下收到的 `WM_CLOSE` 会把窗口销毁而我们的代码根本没机会跑（实测：窗口没了、进程残留）。正常场景（Alt+F4 时窗口是可见的）没问题；真要兜住得子类化窗口过程拦 `WM_CLOSE`，目前不值得。
20. **自动化测试里"窗口可见"和"有焦点"是两件事** —— 脚本跑起来时 PowerShell 控制台会抢焦点，MxRun 因为"失焦即隐藏"会自己躲起来，于是后续的 `WM_CLOSE` 打在一个隐藏窗口上，测出来的现象完全不是代码的问题。**要用 `MXRUN_KEEP_OPEN=1` 把窗口按住再测窗口行为**（第一次测 Alt+F4 就是这么假失败的）。
21. **在 `ScrollArea::auto_shrink([false, false])` 之后画的东西，不是被压住就是被挤出卡片**（2026-09-19，用户截图报的重叠）—— 滚动区会把"当前可用高度"全部占掉，之后再画的内容要么没空间只能原地叠上去（`bottom_up` 状态栏就压在最后一行上），要么直接被裁到卡片外面（空状态文字）。**布局顺序要按"先预留后填充"：底部栏/状态栏先 `Panel::bottom(...).show(ui, ..)` 切走、再放会撑满的滚动列表**。顺带记住：`Rect::intersects` 对**共边**（哪怕只差 0）也返回 true，写重叠自检要用"侵入量 > 1px"这类判据。
22. **`SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)` 的模态移动循环会吃掉鼠标消息**（2026-09-19，自动化验证挖出来的真 bug）—— 它自己抽消息直到松开，于是 **winit/egui 永远收不到"松开"**，egui 保持"指针按着"的状态，**下一次拖动被忽略**（现象：拖一次成功、再拖一次没反应，用户观感就是"拖不动"）。修法：移动循环返回后自己 `PostMessageW(WM_LBUTTONUP)` 补一条。**推论**：任何"把控制权交给系统模态循环"的做法（拖动、菜单、模态对话框）都要想一遍"这期间的消息谁收走了"。
23. **egui 的 `Panel` 会吃掉自己边缘的按下事件**（2026-09-19）—— 面板为"拖拽调整大小"在边缘注册了 `click_and_drag`，即使 `resizable(false)`，压在它上面的拖拽手柄仍收不到按下。要那块区域可拖，就在面板之后**再注册一层**同矩形的 `Sense::drag()` interact（egui 里后注册的在上）。
24. **PowerShell 5.1 读无 BOM 的 UTF-8 `.ps1` 会按 GBK 解析**（2026-09-19，老坑重演）—— 中文注释直接变成语法错误（"Missing using directive"之类莫名其妙的报错）。仓库里的 .ps1 一律**存成 UTF-8 with BOM**；用 `[System.IO.File]::WriteAllBytes` 在前面加 `EF BB BF` 即可（字节级操作，不要走 `Get-Content`/`Set-Content`）。
25. **"悬停即选中"会毁掉键盘流**（2026-09-19，用户报告）—— 鼠标停在列表上时，↑↓ 每动一次就被悬停抢回原项，用户观感是"上下键坏了"。原版 AltRun 的列表**没有 `OnMouseMove`**：选中只由键盘、左键、右键（先模拟左键选中）改变。**教训：鼠标悬停只能做"视觉反馈"，绝不能改状态**；顺带记一条测试心得——**故意把 bug 加回去、确认测试会失败**，否则不知道那个测试有没有用。

## 8. 环境与操作要点

```bash
export PATH="<MinGW-w64>/bin:$HOME/.cargo/bin:$PATH"   # 真实路径见 local/机器环境.md
cd <项目目录>
cargo build --release     # → target/release/mxrun.exe（构建前先关掉运行中的实例）
cargo test                # 51 项单元测试（模型/迁移/搜索/执行器/导入器/参数提示）
```

- 数据目录 `%APPDATA%\MxRun\`（`mxrun.redb` + `backups/` + `mxrun.log` + `inbox/`）
  - **便携模式**：exe 旁边放一个空的 `portable.txt` → 数据全部改到 exe 旁的 `data\`（数据库/备份/日志/收件箱），整个文件夹可以随便拷（§2.12）
  - 同一台机器上便携副本与 `%APPDATA%` 正式版是**两个独立数据库**，且单实例互斥体是全局的——别同时跑
- **`mxrun.log` 是排查主力**：记录 renderer / `index:` 索引构建 / `frame: first` 冷启动首帧 / `icons:` 图标（首帧就绪、worker 空闲）/ `wake:` 呼出延迟 / `hide:` / `execute:` / `import:`。写代码时值得继续往里加事件
- 用独立数据目录做实验：`APPDATA="$TEMP/mxrun-test" ./target/release/mxrun.exe`
  （注意：单实例互斥体是**全局**的，不随 APPDATA 变化）
- 温度开关：`MXRUN_RENDERER=wgpu`、`MXRUN_BACKDROP=acrylic`、`MXRUN_CARD_ALPHA=n`、`MXRUN_KEEP_OPEN=1`（关掉"失焦即隐藏"，方便盯着窗口看/排查）
- **导入开关**：`mxrun.exe --import`（精选）/ `--import-all`（全量）；源文件默认取 `$MXRUN_ALTRUN_LIST`，也可在开关后面直接给路径
- **右键集成开关**：`mxrun.exe --install-integration` / `--uninstall-integration`（等于设置页那两个按钮：写 `SendTo\MxRun.lnk` + `HKCU\Software\Classes\{*|Directory|Directory\Background}\shell\MxRun`）。两者都会弹一个 Win32 汇总框（见踩坑 15）
- **自动发现**：默认开（`cfg:discovery=0` 关闭）。设置页有开关 +"现在扫一次"；扫描在**首帧之后**的后台线程跑，按 `(路径, mtime, 大小)` 增量；日志事件 `discover: scan started` / `discover: seen=… added=… in Nms`
- **便携**：exe 旁边建一个空的 `portable.txt` 即可（数据进 `data\`）；移动/改名文件夹后**跑一次就自动修正**注册路径
- **机器本地状态**：`%LOCALAPPDATA%\MxRun\integration-asked` = "这台机器已经问过要不要集成"（故意与数据目录分开，见 §2.12）
- **加项命令行**：`mxrun.exe "<路径>"`（可多个）——已有实例在跑就交接给它并静默退出；没有实例则以卡片尺寸启动并直接打开确认框
- **隐私（2026-09-14 起，仓库是公开的）**：个人路径/用户名/软件清单一律不进被跟踪的文件——放 `local/`（已忽略），文档用 `<占位符>`。
  `.githooks/pre-commit` 会在提交前扫描并拦截（拦截词在 `local/personal-patterns.txt`）。**换机器 clone 后要执行一次 `git config core.hooksPath .githooks`**，否则钩子不生效。
  提交前自查：`git grep -n -E "<你的私有关键词>"`（钩子偶尔会被 `--no-verify` 绕过）。
  ⚠️ 参数历史存在库里（`param:` 键），跟原版的 `ParamHistory.txt` 一样是**明文**——搜过的词、路径都在里面，这是功能本身要的；但**不要把它打进日志或导出到仓库**（`export_json` 不含它）。
- **自检开关（无键盘验收用）**：`MXRUN_SELFTEST=<查询>` 启动时自动填入关键字、跑**真实**搜索，把每行结果（标题/类别/是否需要输入/得分）写进 `mxrun.log`；再加 `MXRUN_SELFTEST_EXEC=1` 会执行第一行（只对"拒绝执行"的条目安全，比如需要输入的）。
  需要参数的条目：`MXRUN_SELFTEST_EXEC=1` 会**打开参数提示**（不执行），再加 `MXRUN_SELFTEST_PARAM=<文本>` 才会真的把参数交给命令行执行——**它会真执行**，务必配一个无副作用的样本条目（样本档案里的 `p11` 就是：写一个临时文件，见 §2.10）。
  **`MXRUN_SELFTEST_ADD=1`**：收到交接进来的路径后自动把确认卡"按两次回车"走完（第一次警告关键字撞车、第二次覆盖），用于验证右键链路；**它会真的写库**。**`MXRUN_SELFTEST_EDIT=1`**：对第一行执行 F2 编辑 → 改命令行 → 保存，验证 id/启动次数不丢；**同样会真的改库**。这两个只对**临时档案**用（`$env:APPDATA=$env:TEMP\...`）。
  **`MXRUN_SELFTEST_MANAGE=1`** 打开管理器、**`MXRUN_SELFTEST_DELETE=1`** 顺手删除选中项（**真删**）、**`MXRUN_SELFTEST_SOURCE=discovered|curated`** 先按来源筛选；**`MXRUN_SELFTEST_DISCOVER=force`** 忽略缓存全量重扫开始菜单。
  **这是唯一能在没人按键的情况下验证"搜索 → 列表 → 参数 → 执行"链路的办法**——`SendKeys` 只会送进当前前台窗口（踩坑 3），自动化环境里会误伤别的窗口。
  实测输出示例（查询 `dos`）：`row0 title="Dos窗口" category=命令 needs_input=true score=1088.0`；`p11` 与加项链路见 §2.10 / §2.11。
